# Independent PropertyGuru PostgreSQL + local Neo4j audit

## Remediation (after independent audit)

- Fixed #1: card-only crawls no longer upsert shared `agents`; graph prefers the listing's protected agent/agency values. Added card-only and optional PG replay/graph assertions.
- Fixed #2: on a successful detail fetch with an image payload, obsolete `DETAIL_PAGE` URLs are removed in the same PG transaction; homepage rows and failed/card-only detail runs are untouched. Optional PG tests cover replacement, empty gallery and replay.
- #3 is an **unresolved data-policy limitation**, not safe to fix by clearing all nulls: the cleaner falls back to card data and absent detail keys do not prove removal. Missing agent/project/address fields retain old values; graph links may remain until verified/manual correction. Documented rather than deleting potentially valid data.
- Fixed #4 for legacy `properties` tables missing nullable model columns/indexes; `init-db` remains idempotent. Optional PG regression uses an isolated minimal legacy schema. It is **not** a full migration system: mismatched existing types/constraints and incomplete other tables still require manual migration.
- Fixed #5: `--all-pages` stops with errors on empty/failed pages without pagination, and missing detail-map URLs count as errors; offline regressions added. A valid but incorrect pagination total is still trusted.
- #6 is a **configuration-only caveat**: Compose now requires an explicit `NEO4J_PASSWORD` (minimum eight characters on initial Neo4j setup); the CLI's standalone default is not a supported Compose setup. Persisted-volume password rotation remains manual.

Verification after fixes: `PYTHONPATH=propertyguru_scraper python3 -m pytest propertyguru_scraper/tests -q` **17 passed, 3 skipped** (PG integration skipped: no `PROPERTYGURU_TEST_DATABASE_URL`); `python3 -m unittest discover -s tests -p 'test_*.py'` **7 passed**. `npm run build` and `npm test` remain blocked by missing `node_modules` (`pg`/LangChain/node types and `tsx`); no install attempted. No live PropertyGuru request, PostgreSQL/Neo4j mutation or Bolt connection was made. Optional PG migration/replay/rollback tests and real Neo4j Cypher/relationship cleanup remain unverified without isolated test services. Full graph sync still does not delete nodes for removed PG listings, and cursor 0 still excludes nonpositive listing IDs (normal source IDs are positive).

## Findings (priority order)

1. **High — A card-only rerun can overwrite the detail agent in the graph.** `database.py:45-49,72-80` protects `Property.agent_name` when `detail_fetched` was previously true, but `pipeline.py:147-150` still extracts the card agent; `database.py:99-110` overwrites `Agent.name` on every upsert. `graph.py:103-107` selects `coalesce(Agent.name, Property.agent_name)` (and likewise agency), so the *less authoritative* card name takes precedence in the projection. Repro with the existing `FakeScraper` (`tests/test_persistence.py:20-40`): run once with details (`Detail Agent`), then run with `fetch_details=False` (`Card Agent`), and query `agents.name` / `list(iter_listing_batches(pg))[0][0]['agent_name']`; these become `Card Agent` even though `properties.agent_name` remains `Detail Agent`. Existing replay test (`tests/test_persistence.py:133-144`) checks only the property, not the agent/graph after replay. Requires optional test PG for database execution; code paths independently inspected.

2. **High — Replacing detail images leaves obsolete child rows.** `database.py:86-96` only inserts `(listing_id, source_page, image_url)` with `DO NOTHING`; `pipeline.py:152-154,173-178` never deletes images from an earlier successful detail fetch. Repro: save listing 101 with `detail_images` containing URL A and child `DETAIL_PAGE/A`; on the next successful detail fetch save JSON with only URL B and child `DETAIL_PAGE/B`. `properties.detail_images` becomes B but `property_images` still contains A and B; exports/stats continue to report withdrawn detail images. No test replaces an image URL (`tests/test_persistence.py:125-144` only checks identical rerun).

3. **Medium — Fresh detail pages cannot clear stale identifiers/relationships in PG.** In `database.py:71-80`, `coalesce(excluded[field], old[field])` applies even on `detail_fetched=True` rows for `agent_id`, `project_id`, address fields, etc. `cleaner.py:248-293` can provide `None` for missing agent or project on a later detail page. Repro: detail-sync listing with agent 30/project 20, then successfully fetch a detail page without an agent/project and save it; old PG IDs persist. `graph.py:36-54` *can* clear Neo4j links when its input IDs are null, but the normal ingestion path never supplies null after the first non-null ID, so old `LISTED_BY`/`IN_PROJECT` links remain after sync. The policy may intentionally retain data on partial pages, but there is no distinction between an omitted field and a confirmed removal.

4. **Medium — `init-db` is not a general schema upgrade for an existing table.** `database.py:23-37` adds only nine hard-coded `properties` columns then calls SQLAlchemy `create_all`, which skips an already-existing table (including its index creation). Repro in an isolated *test* schema: create legacy `properties(listing_id bigint primary key, listing_type varchar(20) not null)` and run `init_db()`; it reports success, but `sync-graph`'s `graph.py:103-115` SELECT fails because columns such as `nearest_mrt`, `postal_code` and `title` were not added. Even when missing only an index, `create_all` does not add that index on the existing table. The optional PG fixture at `tests/test_persistence.py:89-99` tests only empty-schema creation and repeating it, not migration of an existing incomplete table. Scope: relevant to legacy/manual schemas, not a fresh schema or a table created with the complete current `models.py`.

5. **Medium — `--all-pages` cannot terminate on a run of failed/empty pages without pagination.** `main.py:47` maps `--all-pages` to `max_pages=None`; `pipeline.py:59-85,200-204` increments the page indefinitely if `fetch_page` raises or returns `([], {})`: there is no page limit, terminal condition or failure threshold. Repro with a fake scraper that always raises in `fetch_page`, invoking `run_sync(max_pages=None)` (must interrupt externally); it never returns or produces a CLI exit status. For finite `--pages` it exits nonzero, as tested. Also, when a concurrent detail fetch returns an empty map rather than an entry for a URL, `pipeline.py:112-123` does not count that failure, so a run can return success despite no details; only explicitly present empty entries are errors.

6. **Low — Defaults without `.env` do not constitute a working local Neo4j setup.** `compose.yaml:9` falls back to `neo4j/password` and `graph.py:136-139` uses the same default, but Neo4j 5 initial authentication requires a password of at least eight characters. The *documented* `.env.example:20-25` password is long enough, and README instructs using `--env-file`; this affects invocations that omit that setup. Password rotation with a persisted volume is correctly documented.

This is a conditional limitation for nonpositive PG IDs (normal PropertyGuru IDs are positive); `map_listing(None)` returns `None`. `--limit` and batch counts for positive IDs, replay clearing with supplied null keys, and failure exit status are exercised by the fake graph tests.
- PostgreSQL rollback on child-insert failure, advisory-lock dedup under concurrency, legacy-schema migration, and actual Neo4j uniqueness/cleanup could not be integration-verified without services. Static path check: `database.py:139-156` saves parent before children in one transaction, rolls back and re-raises on any exception; `main.py:136-160` only syncs graph after a crawl with zero reported errors and exits nonzero on graph failure. CLI renders the PG URL with hidden password (`main.py:58`); `.env.example` separates the LangGraph PG URL from the scraper URL, and the documented Compose/CLI environment uses the same Neo4j password. Full graph sync does not remove nodes whose PG listing was deleted (`README.md`, PropertyGuru section, and scraper README explicitly document this limitation).
