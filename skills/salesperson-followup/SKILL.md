根据用户明确选择生成经纪人联系、看房或总结草稿。选择序号必须绑定用户看到的 recommendation request_id。联系人由用户人工核实；公开挂牌电话只通过选定房源的受控联系人线索接口展示，不进入模型上下文，不从通用数据接口绕过白名单取得电话。号码不能证明使用 WhatsApp 或 Telegram，只有当前用户对同一房源保存的已核实渠道可作为待再次确认的候选。

当前已核验及待核实候选均可生成询问草稿，明确违反硬条件或不在当前列表中的房源不能沿用此推荐跟进。卡片操作使用稳定 listing_id，页面统一编号；不能把两个分组的第1名混为同一套。待核实候选的未知硬条件必须逐项写入核实清单，保留证据 ID 和原推荐版本，不能把发起咨询、模拟执行或双方愿意看房当作条件核验通过。

消息只能询问尚未核实的当前可租、家具和租期，不能承诺符合条件或已经预约。生成草稿与执行是独立操作；编辑内容或收件人使旧审批失效。模型没有 execute_action 权限。

看房使用服务器实际日期及 Asia/Singapore 时区，起止时间必须合法，本地日历检查重叠。供应商受理不代表双方同意；双方同意须分别留有记录。执行以服务端 simulation/live 配置为准，不能由模型修改。仅支持 WhatsApp Cloud API 和 Telegram Bot API；无凭证时不得声称真的发送。WhatsApp 窗口外需获批模板，Telegram 收件人先联系机器人，联系人关系与联系许可需用户核实。内容、收件人、模板、时间变化使旧审批失效。

协商诉求保留为用户意向，不能写成经纪人已经同意。发送通过持久队列且不自动重试；UNKNOWN 状态需人工核对。回信只关联明确的回复或唯一动作，不能把回复当作条件核实通过。跟进提醒独立于已发送正文，可调整、完成或取消，仅产生应用内通知，不自动发送第二封消息。日总结区分当天事件与生成时的需求、动作快照。

总结保留需求版本、推荐顺序、快照范围、未知项、下一步和来源。停止条件：保存可审阅草稿或生成受控模板文档；等待核实、审批或选择补充。
