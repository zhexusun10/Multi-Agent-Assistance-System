# 需求卡片补充后的解释失败、预算摘要及列表展示修复

## 真实失败记录

2026-10-24检查会话任务记录，最近两次失败都发生在Explanation阶段。用户提交的结构化答案为挂牌面积500–1500 sqft、必须满足，以及ideal_rent选择any（目前预算即可）。Requirement正常合并，3000新币硬预算、1间卧室和原房型均保留；Recommendation已经返回5套正式推荐、4套待核实房源。不是面积或预算字段匹配失败。

错误记录为：`EXPLANATION_GENERATION_FAILED: GROUNDING: numbers 4 are not supported ...`，对应Hillview Green的介绍。此前没有持久保存失败文稿，因此只能确认数字引用检查拒绝了“4”，不能据日志断言正文中“4”的具体语义。本次补齐比较范围内“其他4套”和“第4套”等数量、序号的上下文校验；它们不会被当成租金、面积或设施数量。真实的4间卧室、4分钟仍必须有对应数据，不能借比较数量通过校验。

## 本次修改

- 卡片的any答案按题型解释。ideal_rent的any明确显示“保留原预算上限3,000新币，不新增理想月租偏好”，不改原硬预算。closer的any表示保留范围、不新增更近偏好；其他题型才使用“不限”。前端预览和服务端摘要一致。
- 旧卡片及自动生成的提交消息在公开状态中校正文案，原始答案、操作记录和历史存档不改写。仅精确匹配系统生成的卡片提交文本，不修改用户自己输入的自然语言消息。
- 公开状态返回前，服务端同样执行共享Top5选择器；旧客户端即使拼接两组，也只会收到合计5套。原始推荐及完整证据仍保留。静态页面/脚本使用no-store，入口版本更新；状态同步识别presentation_version变化，避免业务版本未变时忽略展示修复。
- 正常解释仍走LLM写作、严格结构与数值引用检查、独立语义复核和有限纠错。写作或服务失败后，保存诊断与最后输出，使用已接受的房源事实组织简短逐套介绍，再通过同一份确定性校验。不得复用失败文稿或编造事实。后台标记`evidence_recovery`及`semantic_audit=not_run`；不把这条恢复路径谎称为模型复核通过。身份、数据来源和请求不匹配仍停止。
- 有效推荐已完成时，不再因为介绍文案失败，把整个找房轮次标为失败。未知地点距离仍明确提醒确认，不能因此宣称房源靠近目标区域。

## 验证和恢复

使用真实失败轮次的要求、5+4推荐报文和5套已存详情离线回放；回放快照不含密钥或经纪人联系方式。已验证500–1500 sqft合并后与真实保存要求一致，硬预算3000新币不变；生成5条带引用介绍，保留CLEMENTI距离未知说明。模拟写作服务失败后不再追加付费调用，诊断保存且事实介绍通过校验。

浏览器实际填写500、1500、sqft、必须满足，随后选择“目前预算即可”；预览及提交后均明确保留3,000新币，显示5条介绍、5个编号和5张卡片。浏览器业务接口拦截，不请求付费模型。另验证新版展示可在业务revision相同的情况下更新。

`scripts/recover-saved-explanation.ts`默认只校验和预览；带`--apply`时，仅修复指定且仍为当前的失败解释轮次。它要求原推荐已接受、没有会话内运行任务，保留原失败任务、错误和原始推荐；原子保存恢复说明、更新会话并发出结果事件。不搜索或改排序，不调用模型。
