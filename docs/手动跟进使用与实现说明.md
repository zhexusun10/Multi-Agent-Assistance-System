# 手动跟进：复制草稿、记录发送、贴回回复

本流程不需要 WhatsApp、Telegram 或 PropertyGuru 的 API 凭证。系统不打开外部链接，也不代发消息。

## 使用步骤

1. 在推荐房源中点击“联系经纪人”，进入“跟进工作台”。待核实候选也可以咨询，未确认事项会写进草稿。
2. 点击“编辑草稿”。默认方式是“复制草稿，自行发送”；修改正文和协商诉求。看房草稿需要填写新加坡时间的候选起止时间。点击“保存当前草稿”。
3. 点击“复制草稿 / 确认已发送”，核对完整正文，点击“复制完整草稿”。自行切换到你使用的联系平台，核对经纪人并粘贴发送。浏览器禁止自动复制时，可在正文框全选复制。
4. 发送完成后回来勾选“我已核对收件人和正文，并已在外部平台自行发送这段内容”，点击“确认已发送”。复制和打开窗口都不会自动标记为已发送。
5. 收到经纪人回复后点击“粘贴回复 / 已收到回复”，粘贴原文，勾选来源确认，点击“已收到回复，保存并理解”。原文先持久保存，模型理解在后台进行。
6. 卡片和对话中会显示回复理解、与发送时必要条件的对照、尚待核实事项及下一步。可“根据回复起草下一步”，编辑保存后重复复制流程。草稿不会自动发送。
7. 可设置等待回复或看房提醒；回复只完成等待回复提醒。看房仍须单独点击“记录双方同意”，填写双方明确同意的依据。最后在“总结文档”生成当天会话与跟进总结。

日期面板统一按新加坡时间选择。点日期和调整时分时先暂存，点击“确认保存”才写回当前输入框；点击“清除”会清空该字段。今天用小圆点标记，只有当前选择的日期使用深色背景。按 Esc 或点击面板外可以放弃尚未确认的选择。看房时间选好后，仍需点击“保存当前草稿”保存整份草稿。

## 业务语义

- 对外草稿使用租客第一人称的自然问句。内部生成指令、证据缺失说明、历史快照提示和预约状态留在工作台，不拼进发给经纪人的正文。协商诉求只包含用户真实填写或提出的内容。
- 例如底层存储的 `2026-10-21T06:00:00Z` 至 `07:00:00Z`，消息显示为“2026年10月21日（周三）2:00 PM–3:00 PM（新加坡时间）”。预览、复制和发送共用同一格式函数；底层仍用带时区的时间戳保存和校验。
- 已存在的旧格式草稿，进入编辑或尝试复制时会先重新起草为自然消息，核对并保存后再复制。真实协商诉求和已选看房时间会保留；已经确认发送的历史正文保持原样。
- “用户确认已发送”仅表示用户自行发送的声明，没有平台送达、已读或身份认证回执。
- “已收到回复（用户粘贴）”仅表示用户提供了原文。对方表示符合条件不等于已核验房源事实，也不会把推荐卡片的“待核实”自动改为通过。
- 回复理解会分别记录最短租期、家具清单、床品、水电和其他费用；“配备独立卫浴”会显示“对方表示有独立卫浴”，不会再因缺少“有/带”这样的固定动词被判成未知。水电包含不等于没有押金或其他费用，列出了家具也不等于全套家具齐全。
- 同一用户、同一房源、同一搜索与需求版本下，多轮回复会累积理解。例如第一次回答租期、家具、独立卫浴，第二次只回答月租和当前可租，系统仍保留第一次的信息。所有继续起草与重新起草入口共用这些信息，只追问未答清或相互矛盾的事项。已有的旧版理解在继续起草时自动升级；已编辑或已发送的正文不会自动覆盖，可点“重新起草自然消息”核对后保存。
- 原推荐已经通过的地点距离单独显示“原推荐的地点证据符合（非经纪人确认）”，不会因为经纪人未提到距离而反复询问。历史月租不能证明当前租金，仍会询问当前价格；报价冲突、含糊答复、只有卫浴数量等情况继续保留不确定性。
- 月租与押金分开；独立卫浴与卫生间数量分开。例如预算2000、必须独立卫浴，对方回复“月租2200，没有独立卫浴”，两项都列为冲突。“周六可以看房”仍不是双方确认了准确时段。
- 已复制的修订与正文哈希绑定；修改草稿后旧复制快照不能用来确认。用户复制后又搜索，仍可记录原来已自行发送的正文，回复按复制时的需求核对。旧需求的回复不会被直接用于新需求的后续草稿。
- 重新理解、重复确认、网络重试都有去重或版本控制。模型故障时原文不丢失，使用保守规则并标注，可手动重试；服务启动后会恢复未完成的理解任务。

## 实现位置

- `src/domain/manual-followup.ts`：复制快照、确认发送、回复落库、后台理解与恢复、后续草稿。
- `src/domain/reply-analysis.ts`：配置的大模型与按分句处理的规则共同提取带原文依据的声明。支持月租、独立卫浴、可租状态、明确家具类别的对照；最短租期只用于识别过短租期冲突，不擅自认定任意更长租期都被接受。家具物品清单与“全配”分开，已回答话题与平台核验状态分开。
- `migrations/003-manual-followup.sql`：手动回复及理解状态。与真实平台 `messaging_inbound` 分表，不会因此打开 WhatsApp 的24小时服务窗口。
- `frontend/followup.js`：复制、确认、贴回回复、理解卡片及下一步草稿。外部文本按纯文本渲染。
- `frontend/date-time-picker.js`：看房、提醒和总结日期面板；单选日期、暂存与确认、最早/最晚边界及移动端显示。面板底部仅提供“清除”和“确认保存”。
- `src/shared/followup-message.ts`：前后端共用的正文拼接、指令剥离、新加坡本地时间排版；编译后的纯模块通过 `/assets/followup-message.js` 提供给浏览器。
- `src/domain/customer-questions.ts`：把“必须满足”等内部条件标签转换为租客会问的具体问题，保留独立卫浴、家具、租期等需求的原意。
- `src/server.ts`：会话归属校验后的 `manual-prepare/sent/reply/analyze/next` 接口；理解异步执行，不占用前端请求等待模型。

## 验证命令

```powershell
npm run typecheck
npm test
$env:BUSINESS_LIVE='1'
node --env-file=.env --import tsx --test tests/manual-followup-live.test.ts
.venv\Scripts\python.exe scripts/test_manual_followup_ui.py
```

浏览器验收需先启动最新应用，且先运行上述 PostgreSQL 验收生成隔离的合成房源会话。浏览器验收调用项目当前配置的真实模型，但不向任何外部联系人发消息。结果在 `evaluation/reports/manual-followup-*.json`，截图在同目录。合成数据只用于可控测试，不属于真实房源推荐。

回复连续性回归（需要已有 `listing-presentation-ui-fixture.json`，其中推荐来自真实样本搜索；创建独立的测试会话，不改动原会话）：

```powershell
$env:BUSINESS_LIVE='1'
$env:MODEL_LIVE='1'
node --env-file=.env --import tsx --test tests/reply-continuity-live.test.ts
.venv\Scripts\python.exe scripts/test_reply_continuity_ui.py
```

报告 `evaluation/reports/reply-continuity-business.json` 和 `reply-continuity-ui.json` 分别记录真实数据库、多轮记忆、实际模型和浏览器验收。模型不可用时浏览器报告会明确记录 `model_verified=false`，不把规则回退当成模型通过。
