# 交互式需求补充卡片设计方案

状态：方案记录；首版已按后续用户要求采用mock触发实现，见[实现与验收](需求补充卡片_实现与验收.md)。本方案中的真实分数接入、卫浴字段扩展等仍为后续对接范围。

## 1. 触发机制与职责

- 按团队约定：Recommendation 返回本轮“需要补充需求的程度”分数，超过配置阈值，才进入补充卡片流程。不另用“少于几个条件”替代这个触发机制。
- 这是本轮级信号，左侧一次只生成一张补充卡片，不按八套房源各生成一张。
- 当前接口只有房源 explicit_score、implicit_score、combined_score 等字段，尚无专用的需求补充分数。需与 Recommendation 对接分数的字段、取值范围、阈值、版本及缺失语义；不擅自复用 combined_score。
- 阈值由后端配置管理。分数缺失、推荐失败或版本不匹配时，不伪造分数。
- Requirement Agent 负责字段能力登记、选择问题、回答校验及需求合并；Recommendation 负责评分、筛选和排序；Explanation 解释实际推荐结果；Orchestrator 负责派发、等待用户和恢复流程。

流程：Requirement → Recommendation → Explanation → 检查补充分数 → Requirement 生成问题计划 → 左侧卡片等待用户 → 用户提交 → Requirement 校验合并 → Recommendation → Explanation。

等待用户时持久化状态，不持续调用模型，也不让 HTTP 请求一直等待用户填表。

## 2. 当前数据与能力边界

直接读取 data/propertyguru.db 的 RENT 全量记录所得：

| 字段 | 有效记录数 / 21,431 | 当前原生推荐可接收 |
| --- | ---: | --- |
| 月租 price | 21,431 | 是 |
| 卧室数 bedrooms，正数 | 12,520 | 是；0不能当作已知卧室数 |
| 房源挂牌面积 floor_area_sqft，正数 | 13,079 | 是 |
| 房屋类型 property_type | 21,431 | 是 |
| 卫浴数 bathrooms，正数 | 19,826 | 否；需要扩展推荐契约、数据投影和验证 |
| 独立卫浴使用权 | 无可靠结构化字段 | 否；不能由卫浴数量或照片推断 |
| 到地点的直线距离 | 依有效坐标、地点解析和证据而定 | 支持部分地点/类别，必须核对实际返回结果 |
| 实际步行、公共交通或驾车分钟 | 未接路线服务 | 不支持实际核验 |

挂牌面积不等于卧室面积，卫浴数量不等于独立使用权，卧室数量不等于整租/单间。

首版只主动提供能够通过现有推荐链路影响结果的问题。用户在自然语言中主动提出独卫、租期等要求，仍按现有机制保留，并标明证据不足；不能为了避免待核实而删除诉求。

## 3. 首版问题池

| 问题 | 控件 | 提交语义 |
| --- | --- | --- |
| 每月预算最多多少？ | SGD上限输入框；可选增加下限 | 未给预算时优先询问；明确上限为hard，下限只有用户填写才存在 |
| 希望几间卧室？ | 数量按钮/数字输入；恰好、至少、最多；不限/未想好 | 保留比较符，不能将至少2间变成恰好2间 |
| 想优先考虑什么房屋类型？ | 本轮实际出现的常见类型多选；不限 | 只能接受或有更好由用户选择，后台映射已登记枚举 |
| 对房源面积有要求吗？ | 最小面积输入，㎡/sqft；可选区间；不限 | 使用挂牌面积；缺少一致面积口径时不出题；单位由服务器换算 |
| 在预算范围内，希望租金尽量控制在多少？ | 理想月租输入；目前预算即可 | 在原hard上限之外新增soft目标；不得偷偷收紧原预算 |
| 在允许范围内，是否希望离指定地点更近？ | 更近优先/范围内即可 | 仅在未已有相同软偏好时问；更近优先不发明新的硬半径 |
| 希望附近更方便到哪些地点？ | 从本轮有证据的超市、公园等选择，再给距离输入 | 区分类别与目的地；明确直线口径；缺乏证据的MRT/公交联合条件暂不出题 |

首版不主动询问产权、每平方英尺租金、建成年份、代理资历等次要字段。

卫浴数量可作为第二批字段，先由 Recommendation 完整接入接口和验证，再启用问题。独卫可作为后续联系经纪人的核实意向，但不能当作当前有可靠评分证据的自动补充题。

## 4. 如何从本轮房源选择问题

1. 分数达到阈值后，读取当前需求、已问/已答/跳过记录，以及本轮推荐房源的有效事实。
2. 先考虑基础缺项：预算、卧室数。基础缺项用于明确找房对象，不要求它恰好能区分当前八套房源。
3. 其余用于改善排序的问题，必须同时满足：常用字段白名单、推荐接口可接收、本轮有足够有效数据、答案能够改变筛选或排序、用户尚未表达同一语义。
4. 数据覆盖的首版建议值是75%，即8套至少6套有有效值。字段存在但null、空字符串、卧室0、无效坐标均不计入。
5. 覆盖之外还要检查差异：类别至少有两个有代表性的取值；数值按用户可理解的区间分组，不能只因相差1 sqft就认为值得提问。所有已知值相同则跳过。
6. 先选择覆盖更好、差异更明显、用户更容易回答的字段，一张卡片最多3项。完全相同的硬条件和系统已经保存的软偏好不重复问。
7. 缺少新字段时，可问已有硬上限以内的理想目标，例如预算3000内、是否希望尽量2500内。这是用户明确新增的soft偏好，不替换3000的hard条件。

已经评分的房源与待核实房源分别统计，未评分的占位0分不能用于分数接近程度计算。字段分析可以参考本轮全部展示房源，但不能把缺失值当作不满足。

本轮八套只用于选择值得询问的问题。提交答案后重新搜索完整房源库，不能只在这八套中重排，否则用户会被第一轮候选限制。

保存的NUS需求修改样例中：八套房源的有效卧室数只有4套且均为1，面积及类型各8套有值；类型为Apartment/HDB Flat，卫浴数为1/2。这个例子说明：有值、存在差异、接口支持是三项不同条件。面积仍需检查挂牌口径，卫浴数仍需接通推荐接口。

## 5. 回答语义

- 每题均有不限、暂未想好或跳过；不预选会改变需求的答案。
- 数字输入优先采用输入框加步进按钮，区间下限、上限分开填写。拖动条可以辅助，不作为唯一操作方式。
- 除明确预算上限等表述外，用户需要选择必须满足或有更好；不能把所有新答案默认变成hard。
- “不限”表示不设置这项限制；“跳过”表示本次没有表达偏好，不代表相反要求。
- 若将来增加独卫题，选“可以接受共用”表示不要求独卫，不能编码成必须没有独卫。
- 对已有条件给出的修改，应在提交摘要中明确显示；无关旧条件全部保留。
- 不从候选分布、按钮点击顺序或用户停留时间推断新需求。范围建议不预填成已同意的答案。

## 6. 聊天中的卡片交互

- 放在对应Explanation消息下方，属于左侧历史消息内容，随聊天滚动，不悬浮、不占右侧房源卡片空间。
- 一张卡片分页展示最多3题；展示当前题序。上一项、下一项控制翻页，已填内容保留。
- 最后一页展示本次新增/修改的简短摘要，按钮为“补充好了，重新推荐”；另有“暂不补充”。
- 仅在用户点击最终按钮后合并需求并重新推荐。翻页、选择或输入时不改变当前推荐列表，不调用模型。
- 全部跳过时关闭卡片，不发起一次没有变化的推荐。
- 草稿持久化以支持刷新恢复。提交后卡片保留为历史记录并只读，清楚显示用户当时的选择。
- 如果用户在聊天里修改了需求，旧版本卡片停止提交，避免旧答案覆盖新需求；已填草稿不静默丢弃。

## 7. 停止询问和防重复

每次重新推荐后仍按Recommendation的新分数判定。分数不超过阈值则不生成新卡片。

即使分数仍高，以下情况也不重复打扰：用户明确暂不补充、没有可操作且未问过的问题、下一张只有刚被跳过的相同问题。拒绝补充的标记不作为筛选条件，也不影响房源评分。

已表达硬条件不等于用户同时同意同字段的软目标；相同地点的重复软条件也不能通过改标签再次询问。已回答或跳过状态按会话和问题语义保存，用户主动改变找房目标时再重新评估是否适用。

不以“已收集5个字段”作为唯一停止标准，也不强迫用户制造偏好。用户确实只在意预算和地点时，允许保留这组需求。

## 8. 后端提交、版本和职责

卡片计划关联session、source_request、requirements_version及唯一plan_id。前端提交字段答案，不把答案拼成自然语言再让LLM重提取。

Requirement端按白名单校验字段、枚举、数值、单位、上下界、比较符、hard/soft及旧版本，确定性生成现有需求补丁，再调用既有需求合并逻辑。新需求通过版本检查后进入完整Recommendation和Explanation流程。

一次提交使用幂等键，重复点击不启动两轮推荐。会话所有者及卡片来源由服务器校验；前端传回的候选统计、阈值或分数不能被视为可信依据。

建议新增模块：

- src/agents/requirement/refinement/：问题字段登记、有效值统计、问题计划、结构化提交校验。
- frontend/requirement-refinement.js：聊天卡片、翻页、草稿、提交和只读历史状态。
- src/contracts/requirement-refinement.ts：分数信号、问题计划和答案契约。
- migrations/005-requirement-refinement.sql：卡片计划、回答、草稿及去重状态。

在workflow的Explanation完成处接入计划生成；保持正常聊天需求提取、原生推荐评分和解释校验的既有职责。

“面积更大优先、租金更低优先”若采用连续偏好，需要将原生已有utility能力在适配器完整映射；当前适配器主要给距离使用proximity，不能只改前端按钮就声称已接通。

## 9. 实施顺序与验收

1. 与Recommendation锁定本轮补充分数契约；登记首批真正可操作字段。
2. 实现无模型调用的问题规划器，先做覆盖、差异、已答/跳过及未知值测试。
3. 实现左侧历史卡片、草稿恢复、翻页和最终确认。
4. 接通结构化提交、旧条件保留、全库重新推荐及新Explanation。
5. 接入分数判断与下一轮循环，验证不自动跳动、不卡住执行请求、不重复询问。

验收重点：8套6条有效值边界；字段均相同；卧室0；㎡/sqft换算；恰好/至少；不限与跳过；未知不视为失败；soft不变hard；用户选到当前八套之外的房源；自然语言修改使旧卡片失效；重复提交；刷新恢复；分数下降停止；用户拒绝后停止。

默认使用保存的推荐结果和模拟分数作离线/浏览器验收。翻页、字段规划、草稿保存、结构化提交不增加LLM提取请求；只有用户最终要求重新推荐才进入正常模型流程。真实模型测试遵守AGENTS.md的费用限制。
