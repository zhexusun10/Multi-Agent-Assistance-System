# 平台代发消息：Telegram 与 WhatsApp 逐步操作教程

适用项目：`D:\Real Estate Agent\Multi-Agent-Assistance-System`。

核对日期：2026-10-19。本文采用你已选定的方式：找房用户在网页批准消息，后台以项目的 Telegram 机器人或 WhatsApp 业务号码发送；经纪人向这个平台账号回复，本地系统接收。不是登录租房用户的个人聊天账号。

建议按顺序完成 Telegram → WhatsApp 测试号码 → 正式业务号码。Telegram 先跑通后即可演示真实发送、接收文字回复和跟进；WhatsApp 还要配置 HTTPS webhook。

## 0. 开始前准备

- 打开 Docker Desktop，保留现有数据库。
- 需要 Windows PowerShell、项目现有 Node.js 和 `.venv`，无需重装模型和数据依赖。
- Telegram：可正常使用的账号，测试收件人可以是你自己或小组成员。
- WhatsApp：可登录的 Meta 开发者账号，以及用于接收测试消息的个人 WhatsApp 号码。初期发送方使用 Meta 控制台提供的测试号码。
- 所有密钥仅保存在本机 `.env`，不要放进聊天、截图或 Git。

打开 PowerShell，进入项目：

```powershell
Set-Location 'D:\Real Estate Agent\Multi-Agent-Assistance-System'
```

打开配置文件：

```powershell
notepad .env
```

只修改下文对应的配置行。保留原有模型、数据库等配置；每个键只留一行，不要把整个 `.env` 替换成示例片段。示例中的中文说明必须换成你自己的实际值。

当前代码支持真实平台接口，但尚未配置平台凭证。不要把代码测试通过理解成已经用真实账号发送成功。

## 1. Telegram：创建项目机器人

### 1.1 打开官方 BotFather

先打开并登录手机或电脑上的 Telegram 应用，再在应用内搜索准确用户名 `@BotFather`，核对官方认证标识，进入实际聊天窗口。如果使用网页版，先打开 [Telegram Web](https://web.telegram.org/) 并登录，再在网页聊天界面的搜索栏里搜索 `@BotFather`。

`t.me/BotFather` 是介绍和跳转页面，其中的 **Start Bot** 用来唤起 Telegram；它不是一个可直接输入消息的网页聊天窗口。如果点击后仍停在介绍页，先绕过这个跳转，按上面的方式在已登录的 Telegram 内搜索。尚无账号时先在官方 Telegram 应用完成注册和登录。

在 Telegram 打开 [https://t.me/BotFather](https://t.me/BotFather)，确认是官方 BotFather，进入聊天并点击 Start。

发送：

```text
/newbot
```

按提示依次提供：

1. **机器人显示名称**，例如 `Qiju SG Rental Assistant`。
2. **唯一用户名**，例如 `qiju_sg_group6_assistant_bot`。如果用户名已被占用，换一个；按 BotFather 提示选择可用的用户名。

创建完成后，BotFather 会给你机器人链接和一段 Token。Token 认证的是机器人，不是你的个人账号。[Telegram 官方创建教程](https://core.telegram.org/bots/tutorial)

### 1.2 把 Token 填入项目

先停止项目应用，避免后面的 chat_id 检查与后台轮询争抢更新：

```powershell
.\scripts\stop-app.ps1
```

在 `.env` 找到并修改：

```dotenv
TELEGRAM_BOT_TOKEN=粘贴BotFather给你的实际Token
TELEGRAM_RECEIVE_MODE=polling
EXTERNAL_ACTION_MODE=simulation
```

暂时保留 simulation，取到正确收件人后再切换 live。`TELEGRAM_WEBHOOK_SECRET` 和 `PUBLIC_BASE_URL` 在 Telegram 本地 polling 模式下可以保持空白。这里不需要 `api_id`、`api_hash`，也不需要开启 Secretary Mode。

### 1.3 让测试收件人先联系机器人

将 BotFather 给出的机器人链接发给测试收件人，例如：

```text
https://t.me/你实际创建的机器人用户名
```

收件人打开它，点击 Start，并发送一条新消息：

```text
/start
```

也可以继续发送：

```text
我同意接收本次找房项目测试消息。
```

没有自动回复也正常：当前项目不设置 `/start` 自动欢迎语。关键是收件人确实向机器人发出了新消息。普通机器人不能仅凭别人的手机号或私人用户名就主动发起私人会话。[官方机器人说明](https://core.telegram.org/bots#how-are-bots-different-from-users)

### 1.4 读取并核实 chat_id

保持项目应用停止，在项目 PowerShell 中运行：

```powershell
node --env-file=.env --import tsx scripts/messaging-setup.ts telegram-info
```

预期输出类似下面这样；这是示意数据：

```json
{
  "bot_username": "你实际创建的机器人用户名",
  "bot_link": "https://t.me/你实际创建的机器人用户名",
  "webhook_set": false
}
{
  "recent_chats": [
    {"chat_id": "123456789", "type": "private", "name": "测试收件人"}
  ]
}
```

核对用户名确实是刚创建的机器人，再核对 `recent_chats` 中的联系人。保存对应的数字 `chat_id`，例如 `123456789`。这个数字是消息接收方的聊天地址，不是机器人的 Token，也不是电话号码。

如果输出 `webhook_set: true`，先运行：

```powershell
node --env-file=.env --import tsx scripts/messaging-setup.ts telegram-delete-webhook
```

然后让收件人再发一条新消息，重新运行 `telegram-info`。此命令移除旧 webhook，保留待处理消息。Telegram 的 webhook 和 getUpdates 轮询不能同时使用。[getUpdates 官方说明](https://core.telegram.org/bots/api#getupdates)

如果 `recent_chats` 为空：确认对方联系的是同一个机器人，应用没有启动 polling，然后让对方发一条新消息后再检查。已经被旧轮询确认消费的更新不会重新出现在这次查询里。

以后添加新经纪人时也按这个步骤取得并人工核实 chat_id。课堂联调建议使用私人聊天，不把群聊当作某一位经纪人的私人身份。

### 1.5 开启真实发送并启动应用

修改 `.env`：

```dotenv
TELEGRAM_BOT_TOKEN=你已经保存的实际Token
TELEGRAM_RECEIVE_MODE=polling
EXTERNAL_ACTION_MODE=live
```

运行配置检查：

```powershell
node --env-file=.env --import tsx scripts/messaging-setup.ts status
```

应看到 `mode` 为 `live`，`channels.telegram.configured` 为 `true`。WhatsApp 未配置仍显示 false 不影响 Telegram。`status` 仅检查配置齐全，前面的 `telegram-info` 才实际请求了 Telegram；两者都不证明具体消息已经发送。

启动：

```powershell
.\scripts\start-app.ps1 -SkipDataImport
```

浏览器打开 [http://127.0.0.1:8010/](http://127.0.0.1:8010/)，刷新页面，在跟进草稿中选择“平台 API 发送 / 模拟（高级）”，核对当前渠道状态。

### 1.6 从网页实际发送一条找房消息

1. 先搜索房源，例如：`帮我找D05租房，预算不超过5000新币，至少2房`。
2. 在某套房源卡片点击 **联系经纪人**，该入口同时支持咨询和看房日期选择。
3. 到 **跟进工作台 → 编辑草稿**。
4. 姓名填测试收件人的名字；渠道选择 **Telegram Bot**。
5. 渠道地址填刚核实的数字 chat_id。
6. 测试时明确这是小组测试资料；核对后勾选联系人与接收许可。正式使用时填写实际核实过的经纪人资料。
7. 协商诉求可填：`希望月租协商到4500新币，并核实是否可以提前入住`，点击 **根据诉求重新起草**，检查正文没有承诺对方已经同意。
8. 如果是看房草稿，选择未来日期和候选起止时间；时间按 Asia/Singapore，时长不超过4小时。
9. 点击 **保存当前草稿**，再点击 **批准此修订**，核对弹窗中的收件人和实际发送正文，勾选确认并批准。
10. 点击 **发送到所选平台**。不是“模拟执行”；如果仍看到模拟按钮，检查 `.env` 并重启应用、刷新页面。

预期过程：等待发送 → 正在提交平台 → 平台已受理。测试收件人的 Telegram 应实际收到由项目机器人发出的消息。

### 1.7 接收经纪人回复

让测试收件人在 Telegram 中长按或右键刚收到的消息，选择 **回复 / Reply**，发送：

```text
收到测试咨询。4500可以进一步沟通，独立卫浴还需要核实。
```

保持电脑、网络和本地应用运行，等约5秒并留出网络与界面刷新时间，回到工作台看 **跟进时间线与经纪人回复**。应显示文字回复，动作状态变为已收到回复；对应的“等待回复”提醒会完成。

推荐明确回复那条消息，因为同一机器人可能代表多个用户咨询同一联系人。缺少回复消息ID且对应多条动作时，系统保留为未分配来信，不猜测应该归到哪个用户。

Telegram 普通 Bot API 不提供我们这里可用的个人聊天已读回执，平台已受理和实际收到回复是不同证据。收到文字也不会自动证明房源条件满足或看房已确认。[Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage)

## 2. WhatsApp：先建立测试发送账号

### 2.1 准备发送方和收件人

初次测试包含两个不同号码：

| 角色 | 说明 |
|---|---|
| 平台发送方 | Meta 提供的 WhatsApp 测试业务号码；稍后正式上线可换为自己的业务号码 |
| 测试收件人 | 你自己或小组成员正常使用的 WhatsApp 号码，并在 Meta 测试页面完成允许收件人的验证 |

使用自己的 WhatsApp 号码接收测试，不会让该号码变成平台发送方。平台消息始终来自所配置的业务号码。

### 2.2 创建 Meta 应用并添加 WhatsApp

1. 打开 [Meta for Developers](https://developers.facebook.com/)，用你自己的账号登录并完成页面要求的开发者注册/校验。
2. 进入 **My Apps / 我的应用**，选择 **Create App / 创建应用**。
3. 填应用名称，例如 `Qiju SG Real Estate Assistant`，以及可接收通知的联系邮箱。
4. 选择用于 WhatsApp Business Platform 的用途或产品，并按提示创建或选择你有管理权限的 Business Portfolio。
5. 打开应用的 WhatsApp 设置区域。不同账号界面可能叫 **Get Started、API Setup、API Testing、Getting Started**；寻找包含发送号码、收件人、Token 和测试发送按钮的页面。

具体菜单因控制台版本、账号资格而异；如果没有测试资源或被要求完成额外校验，应按该页面处理，不能保证所有新账号即时获得相同资源。学生团队可先用测试资源联调，不需要把业务验证审核作为 Telegram 演示的前置条件。[Meta 官方开发者入口](https://whatsappbusiness.com/developers/developer-hub/)、[官方 Cloud API 集合](https://www.postman.com/meta/whatsapp-business-platform/collection/wlk6lh4/whatsapp-cloud-api)

### 2.3 获取并分清这些值

| `.env` 配置项 | 去哪里找 / 它是什么 |
|---|---|
| `WHATSAPP_ACCESS_TOKEN` | WhatsApp API 设置/测试页生成的访问令牌；初期通常使用页面提供的临时令牌 |
| `WHATSAPP_PHONE_NUMBER_ID` | 当前测试发送号码的 **Phone Number ID**，不是电话号码本身 |
| `WHATSAPP_BUSINESS_ACCOUNT_ID` | 对应的 **WhatsApp Business Account ID / WABA ID**，不是 Business Portfolio ID |
| `WHATSAPP_GRAPH_API_VERSION` | 使用该控制台请求示例中支持的版本，如 `v数字.数字`；不要把占位说明直接填进去 |
| `WHATSAPP_APP_SECRET` | 当前 Meta 应用 **App settings / Settings → Basic** 中的 App Secret，查看时可能需要再验证账号 |
| `WHATSAPP_VERIFY_TOKEN` | 你自己生成的随机校验串，稍后在 Meta 回调配置中填同一串，不是 Access Token |

要生成 Verify Token，可在本机执行以下命令，把结果自行保存进 `.env`：

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

这个命令只新生成一串随机值，不会读取或输出项目已有密钥。

### 2.4 在 Meta 添加允许的测试收件人

在同一个 WhatsApp API 测试页：

1. From / 发送方选择测试业务号码。
2. To / 收件人处添加你自己的 WhatsApp 号码，选择正确国家代码并按 Meta 提示完成验证码验证。
3. 使用控制台提供的测试消息按钮，先给这个收件人发一条默认测试模板消息，常见示例名为 `hello_world`。
4. 在手机上确认真的收到来自该测试业务号码的消息。

这里的 `hello_world` 仅用于验证 Meta 账号链路；我们的房源草稿不会被后台偷偷替换成它。[Meta 官方测试消息示例](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api?entity=request-13382743-199a6c73-b2c5-4472-9444-71aa029e60ed)

如果控制台自身都发不通，应先解决 Meta 账号、允许收件人、令牌或号码配置，再测试项目。测试号码通常只向控制台已允许的收件人发送，不等于已经能任意联系所有经纪人。

### 2.5 填项目 `.env`

填入你刚取得的真实值，其他原有配置保留：

```dotenv
WHATSAPP_ACCESS_TOKEN=实际访问令牌
WHATSAPP_PHONE_NUMBER_ID=实际发送号码ID
WHATSAPP_BUSINESS_ACCOUNT_ID=实际WABA_ID
WHATSAPP_GRAPH_API_VERSION=控制台示例中的实际版本
WHATSAPP_APP_SECRET=当前应用的实际AppSecret
WHATSAPP_VERIFY_TOKEN=自己生成并保存的随机串
EXTERNAL_ACTION_MODE=live
```

访问令牌须授权对应应用与 WABA/号码。发送涉及 `whatsapp_business_messaging`，管理与读取模板涉及 `whatsapp_business_management`；以账号实际授权和控制台要求为准。临时令牌有有效期，查看控制台显示的到期信息。[Meta 官方样例的权限说明](https://github.com/fbsamples/business-messaging-sample-tech-provider-app)

## 3. WhatsApp：把回复安全送到本机

### 3.1 为什么需要额外入口

Meta 不能访问你电脑上的 `127.0.0.1`。需要一条可从公网访问的 HTTPS 地址，将请求转到本机 webhook。项目提供了只开放两个消息 webhook 的辅助应用 `api/webhook_gateway.py`：

```text
Meta → HTTPS临时隧道 → 本机8011（仅webhook）→ 图服务3001（签名校验和入库）
网页工作台仍只在127.0.0.1:8010使用
```

辅助入口不提供 `/api/state`、`/api/sessions`、网页或文档下载。不要直接把工作台8010、图服务3001、PostgreSQL或Neo4j整体转到公网。

### 3.2 启动项目

在项目 PowerShell 中执行：

```powershell
.\scripts\stop-app.ps1
.\scripts\start-app.ps1 -SkipDataImport
```

确认 [http://127.0.0.1:8010/health](http://127.0.0.1:8010/health) 正常。

### 3.3 启动本机 webhook 辅助入口

新开一个 PowerShell 窗口，运行并保持窗口开启：

```powershell
Set-Location 'D:\Real Estate Agent\Multi-Agent-Assistance-System'
.venv\Scripts\python.exe -m uvicorn api.webhook_gateway:app --host 127.0.0.1 --port 8011 --no-access-log
```

预期看到 `Uvicorn running on http://127.0.0.1:8011`。`--no-access-log` 避免把回调验证查询参数写入此辅助应用的访问日志。签名验证仍由图服务执行，辅助入口不替代 App Secret 校验。

如果你改过图服务端口，先在这个窗口设置正确的 `GRAPH_SERVICE_URL`；默认部署不用修改。

### 3.4 安装并启动临时 HTTPS 隧道

Cloudflare Quick Tunnel 是一个开发测试方案，不需要你先购买域名。Windows 安装方式以[官方 cloudflared 下载页](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/downloads/)为准；使用 winget 可执行：

```powershell
winget install --id Cloudflare.cloudflared -e
```

安装后重新开 PowerShell，确认：

```powershell
cloudflared --version
```

再运行，并保持窗口开启：

```powershell
cloudflared tunnel --url http://127.0.0.1:8011
```

终端会给出一个临时 HTTPS 地址，例如 `https://随机名称.trycloudflare.com`。这是示意，必须使用你自己终端输出的地址。此时只开放了辅助入口，不会开放整个工作台。[Cloudflare Quick Tunnel 官方教程](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)

Quick Tunnel 用于开发测试，重启后地址可能改变；更改后需要更新 Meta 回调。正式部署使用固定域名与稳定服务。此步骤不会由当前聊天自动安装或创建公网隧道，需要你按教程运行。

### 3.5 配置 Meta 回调

返回 Meta 应用的 WhatsApp **Configuration / Webhooks** 配置，可能也在应用的 Webhooks 产品中、对象选择 `whatsapp_business_account`。

填写：

```text
Callback URL:
https://你实际得到的隧道域名/api/webhooks/whatsapp

Verify token:
与.env中WHATSAPP_VERIFY_TOKEN完全相同的值
```

点击 Verify and Save / 验证并保存。成功时 Meta 会请求上述 URL 的 GET 验证，项目校验 Verify Token 并返回 challenge。

然后订阅 **messages** 字段。它包含来信和发送消息的状态事件；同时确认应用与该 WABA 的订阅关系。若控制台没有完成 WABA 订阅，可运行项目辅助命令：

```powershell
node --env-file=.env --import tsx scripts/messaging-setup.ts whatsapp-subscribe
```

该命令会实际把当前应用订阅到所配置的 WABA，不发送聊天消息。它不是代替控制台的回调配置；回调地址、messages 字段和 WABA 订阅关系都应正确。[Meta 官方 WABA 订阅接口](https://www.postman.com/meta/whatsapp-business-platform/request/bw8g53p/subscribe-to-your-waba)

检查只读资产信息：

```powershell
node --env-file=.env --import tsx scripts/messaging-setup.ts whatsapp-info
```

`configured_phone_id_found` 应为 true，输出号码应是你选的测试发送号码。`subscribed_app_count` 只说明存在订阅，不能单凭数量证明其中就是当前应用；`whatsapp-subscribe` 成功以及实际回调才是进一步依据。

Verify Token 用于 GET 回调验证；App Secret 用于 POST 签名验证。二者不能互相替代。项目会校验原始请求体的 `X-Hub-Signature-256`，不要在代理中重新序列化 JSON。[Meta 官方签名验证说明](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/webhooks/start/)

## 4. WhatsApp：先在24小时窗口内发送真实房源草稿

### 4.1 让测试收件人发一条当前来信

完成回调配置并启动图服务后，用测试收件人的 WhatsApp，向之前发送 `hello_world` 的业务号码回复：

```text
我同意接收本次找房项目的测试消息，请开始测试。
```

必须是配置回调之后发出的新来信。Meta 应把这条真实来信送到本机并入库；未关联具体房源的这条初始来信不一定显示在某张动作卡片上，但服务端会记录它的时间。

收到对方来信后的服务窗口内可以发送自由文本；首次主动联系或窗口外联系应使用获批模板，并取得收件人许可。本项目根据验签后的真实来信时间判断，不允许表单自己宣称窗口已经开启。[WhatsApp 官方消息政策](https://business.whatsapp.com/policy)

### 4.2 在网页发送

1. 刷新工作台，选一套房源，生成联系核实或看房草稿。
2. 编辑草稿，渠道选择 **WhatsApp**。
3. 填测试收件人的国际号码，例如新加坡使用 `+65` 加本地号码。输入框中可写 `+65XXXXXXXX`，应换成真实数字；不要填写 Phone Number ID 或 WABA ID。
4. 人工核对联系人和许可；测试时明确这是小组模拟经纪人。
5. 在 WhatsApp 格式中保留 **自由文本（仅限24小时服务窗口内）**。本轮已经有真实来信，不需要等待自定义模板获批。
6. 加入协商诉求；若选看房，填写未来候选时间。
7. 保存 → 审核实际正文 → 批准当前修订 → **发送到所选平台**。

预期：平台受理并返回消息ID，测试收件人手机实际收到房源咨询。若 Meta 回传相应状态，可进一步显示已送达或已读；不能将 API 返回成功当作实际送达。

### 4.3 验证回信与跟进

让收件人使用 WhatsApp 的“回复该条消息”功能，针对刚收到的房源咨询回复。工作台时间线应出现原文，等待回复任务相应完成；经纪人的文字不自动改写房源未知字段。

然后可测试设置提醒、调整提醒、记录双方同意、导出日历和当天会话总结。看房成功仍需客户和经纪人都明确同意具体时段，不能仅根据“可以聊聊”或消息已读就确认。

本机电脑、图服务、8011辅助入口和隧道都要保持运行。只打开浏览器而后台或隧道已停，不能继续接收公网回调。

## 5. WhatsApp：首次主动联系和窗口外的获批模板

正式主动联系经纪人，仍须先取得相应联系许可，并处理窗口限制。不能因为房源页面公开了电话，就认为该电话已开通 WhatsApp或已同意本平台发送。

进入 WhatsApp Manager 的 **Message templates / 消息模板 → Create template**，按真实用途、语言与 Meta 提示选择类别。当前项目支持：

- BODY 文本与可选 FOOTER；
- 按 `{{1}}`、`{{2}}`、`{{3}}` 编号的位置参数；
- 状态为 APPROVED；
- 不带媒体头、按钮或命名参数。

可以参考以下结构写你自己的固定文案，按页面要求提供参数样例并提交审核；这不是保证获批的模板：

```text
Hello, this is Qiju SG rental assistant. With the prospective tenant's approval,
we would like to enquire about property {{1}}.
The tenant's questions and negotiation requests are: {{2}}.
Their proposed viewing times are: {{3}}.
Please confirm current availability and whether the proposed arrangements are possible.
```

获批后，在网页草稿选择 WhatsApp → **读取获批文本模板** → 选择匹配名称和语言 → 填参数。

参数1填房源ID与链接；参数2填待核实事项和协商诉求；参数3填候选起止时间。若是本项目的看房动作，模板正文必须包含这次时段的完整 ISO 字符串，例如 `YYYY-MM-DDTHH:mm:ss.sssZ`，否则项目审批会拦截。以保存时的实际预览为准，不复制过期示例日期。

选择模板会替换自由草稿正文，必须重新检查实际内容。协商诉求应完整出现在最终渲染的模板正文中，不要只留在旁边的备注框。当前读取最多100条模板；不符合支持格式的模板不会显示。

## 6. 从测试号码转为长期运行

Telegram 可继续使用同一项目机器人；保持服务稳定在线。WhatsApp 切换正式业务号码时，按 Meta 控制台完成业务资料、号码归属验证、注册、所需权限/审核和计费配置。准备真实业务名称、联系方式和控制台要求的证明资料，实际要求以账号页面为准，不能保证当天审核完成。

持续运行不要依赖短期测试令牌。可在有权限的 Meta Business Settings / Business Portfolio 中创建或选择系统用户，分配所需应用和 WhatsApp 资产，再按页面生成有适当权限与有效期的令牌。不是申请一个与任何资产无关的“万能API Key”。

换正式号码后要更新对应 Phone Number ID、WABA ID、Token和必要的订阅配置；若应用也更换，还要核对 App Secret。然后重新执行资产检查、接收一条来信、发送一条已批准消息、确认实际回复的完整验收。

## 7. 常见卡点

| 现象 | 优先检查 |
|---|---|
| Telegram Token 未配置或 getMe 失败 | `.env` 是否保存、是否拿错机器人、Token 是否已撤销、网络能否访问 api.telegram.org |
| Telegram recent_chats 为空 | 应用先停止；对方向同一个机器人发一条新消息；确认无旧 webhook |
| Telegram 查询/轮询冲突 | 同一个机器人是否被其他进程轮询；是否仍配置了 webhook；不要让多个项目共用轮询 |
| Telegram 发送被拒绝 | chat_id 是否正确、对方是否先联系机器人、是否把机器人屏蔽了；不能用手机号或私人用户名代替 chat_id |
| 页面仍显示模拟执行 | EXTERNAL_ACTION_MODE 是否为 live；是否重启应用并刷新网页；检查是否有同名重复配置 |
| WhatsApp Verify and Save 失败 | 8011和图服务是否运行、临时域名是否仍有效、URL是否含正确路径、Verify Token 是否完全一致 |
| WhatsApp 验证成功但真实来信不到 | messages 字段、WABA订阅、Phone Number ID、App Secret验签；测试事件成功不等于真实来信成功 |
| WHATSAPP_TEMPLATE_REQUIRED | 没有已验证且24小时内的真实来信；在回调配置完成后发送新来信，或改用获批模板 |
| TEMPLATE_CONFIG / 模板列表失败 | WABA ID与Token及其管理权限；不要把业务组合ID当WABA ID |
| TEMPLATE_MISMATCH | 模板状态、语言、参数与当前正文是否一致，模板是否已被更改 |
| TEMPLATE_CONTENT_REQUIRED | 看房模板未包含完整起止ISO时间或协商诉求，补全参数后重新保存审批 |
| 平台返回400/401/403等 | Token有效期、权限与资产、测试允许收件人、模板和号码状态；在Meta控制台进一步核对 |
| UNKNOWN / NETWORK_RESULT_UNKNOWN | 可能已提交；先在平台和收件人侧核对，不能连续点击重发来碰运气 |
| 回复未显示在某个动作 | 使用平台“回复该条消息”；缺少上下文而同联系人对应多动作时，系统不会猜归属 |
| CALENDAR_CONFLICT | 客户或联系人已有重叠的本地候选时段，请换时间；此前测试记录也会占用对应时段 |

## 8. 最终验收清单

两种平台分别完成：实际收到平台账号发出的房源草稿 → 明确回复该消息 → 网页看到正确动作的回复 → 协商诉求没有丢失 → 提醒能设置/修改/完成 → 看房双方确认单独记录 → 日总结与实际记录一致。

演示结束想恢复模拟，只改这一行并重启项目：

```dotenv
EXTERNAL_ACTION_MODE=simulation
```

```powershell
.\scripts\stop-app.ps1
.\scripts\start-app.ps1 -SkipDataImport
```

如果开了临时隧道和8011辅助入口，在它们各自的终端按 Ctrl+C 结束即可。主项目停止脚本不管理这两个手工启动的辅助进程。
