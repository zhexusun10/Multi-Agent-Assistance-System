# 模糊需求、就近推荐与新加坡地点目录：调研及实施方案

调研及验证日期：2026-10-19。范围：新加坡住宅租赁、现有 Contract V1、当前 PostgreSQL / Neo4j 架构。下文区分研究资料支持的通用方法、本项目的设计选择、已经实际运行的实现，以及尚未部署的扩展。

## 1. 结论与本次纠偏

用户提出的“先满足硬条件，再把离金文泰更近的房源排前”是正确的基础策略。**模糊不等于必须追问**：只说“附近”通常足以确定排序方向，不需要用户查地标或指定公里数。“附近”没有唯一通用的固定半径，也不能被系统偷偷改成“必须 1 公里内”。

需要补充两个边界：如果用户还表达其他软偏好，总排序可以做有说明的多条件权衡，不能同时声称每一项都绝对最优；如果目标是一个区域，必须按区域形状定义距离，不能把区域名称无声替换成同名车站。区域内的多套房源到该区域距离均为 0，属于真实并列。

前一版把“附近”当成必须填写地标、距离和口径的条件，属于过度澄清；其验证脚本也只证明“会澄清”，没有验证用户自然输入能否完成检索。本次已按真实用户旅程纠正。

## 2. 文献和工程资料告诉我们什么

### 2.1 硬约束和软偏好应分开

知识型推荐系统研究区分：以约束保证可行性，以及用属性级相似度或效用对候选排序；后续对话可用批评式反馈修改原偏好。它支持本项目的“先保证条件，再解释排序”路线，但不意味着可以自动放宽用户的明确预算。参见 [Knowledge-based recommender systems: overview and research directions（2024）](https://pmc.ncbi.nlm.nih.gov/articles/PMC10925703/)，尤其 3.2、3.3 节。

本项目据此采用两层：硬条件 pass/fail/unknown 先决定分组；软偏好决定组内顺序。unknown 是证据不足，不是低分的同义词。

### 2.2 “最近”检索不需要先给半径

PostGIS 的官方 KNN 教程明确区分最近邻与距离范围查询：最近邻通过距离排序和 LIMIT 取得最近 N 个，不要求预设多远才算近；`<->` 可利用空间索引。参见 [PostGIS Nearest-Neighbour Searching](https://postgis.net/workshops/en/postgis-intro/knn.html)。

因此，“附近越近越好”可直接建模为 `ORDER BY distance ASC`。如果先擅自截成 1km，再排序，可能把唯一满足预算、卧室等硬条件的 1.2km 房源遗漏。当前样本模式完整评估 475 条租赁候选，不设这样的隐藏截断。

### 2.3 明确半径是另一种操作

“3 公里以内”是可检验的范围条件。PostGIS 推荐用 `ST_DWithin` 做半径过滤，并说明 geography 的距离单位是米；索引是否存在仍需真实部署检查。参见 [ST_DWithin](https://postgis.net/docs/manual-dev/en/ST_DWithin.html) 和 [Use ST_DWithin for radius queries](https://postgis.net/documentation/tips/st-dwithin/)。Elasticsearch 也分别提供 [geo_distance 范围查询](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-geo-distance-query) 与距离打分。

这支持本项目把明确 3km 转成 3000m 硬条件，同时继续在范围内优先更近。上述 PostGIS 方法是可扩展部署方案，**当前 PostgreSQL 容器未安装 PostGIS**，不能把文档 SQL 当作现有功能。

### 2.4 距离衰减适合多个偏好的比较

Elastic 的 [distance_feature](https://www.elastic.co/guide/en/elasticsearch/reference/current/query-dsl-distance-feature-query.html) 使用单调距离函数 `boost × pivot / (pivot + distance)`，其中 pivot 表示分值衰减到一半的距离。其 [function_score](https://www.elastic.co/guide/en/elasticsearch/reference/current/query-dsl-function-score-query.html) 也提供线性、指数和高斯衰减。

本项目选择：`u_near(d)=s/(s+d)`，默认 s=1000m。s 是归一化尺度，**不是用户指定的半径，也不作过滤**；5000m 的候选仍有正分。只有一个就近偏好时，这与按距离升序完全一致；多个软偏好时可归一化加权。

### 2.5 不同模糊词不能一律用距离解决

Göpfert 等人的 [Discovering Personalized Semantics for Soft Attributes in Recommender Systems using Concept Activation Vectors（2023 修订版）](https://arxiv.org/html/2202.02830v3) 讨论开放表达、程度差异及个体语义，提出在已有用户/物品表示和标签数据上学习软属性语义。其电影等实验不能直接证明房地产上的收益。

对本项目的启示是：“附近”有坐标依据，优先用可解释度量；“安静”“高档”“适合我”可能需要噪声数据、标注、评价和用户反馈。**本次没有训练 CAV 或行为推荐模型**，不能因为模型会写解释，就宣称掌握这些属性。

## 3. 可执行的语义策略

| 用户表达 | 系统处理 | 不做什么 |
| --- | --- | --- |
| 金文泰附近 / 越近越好 | 区域就近软偏好，不设置硬半径 | 不要求先给公里数，不默认排除远一些的可行房源 |
| Clementi MRT 附近 3 公里 | 解析站点，3000m 范围硬条件，并保留范围内就近排序 | 不重复问是哪一个地标，不把公里当租金或分钟 |
| 最好在 3 公里内 | 软距离偏好；超出不会单凭此项淘汰 | 不擅自升级成硬条件 |
| 必须在金文泰区域内 | 应使用区域包含关系的硬条件 | 不以邮区 D05 或离车站近代替区域包含；此表达的专门解析仍属后续扩展 |
| 通勤 30 分钟，后来补充公交 | 保留 30min 和目的地，只更新交通方式为 transit | 不拿直线距离、平台 MRT 步行分钟证明真实通勤 |
| 独立卫浴 | amenities/private_bathroom；当前缺证据则 unknown | 不用 bathrooms>=1 证明独立使用权 |
| 安静些 / 更新些 / 宽敞些 | 在对应可观测属性、数据能力和上下文明确后建软偏好 | 不虚构噪声、翻新年份或房间级事实 |

**默认与阈值是两类参数。**内部 `location_intents` 区分无半径与明确 radius_m。无半径时没有该字段；映射到既有 Contract V1 时，soft place_proximity 的数值采用评分参考尺度，来源是已登记的系统政策，不冒称用户报了 1000m。字段版本仍是 1.0，评分版本已经更新为 `baseline-explicit-soft-v2-geospatial-pivot`。队友 B 接入时须共同采用该评分约定，不能把 soft 数值当硬筛选。

## 4. 排序和检索蓝图

### 4.1 分组后排序

对每套候选、每条硬条件计算三值结果：

- 任意硬条件 fail → excluded。
- 无 fail、至少一个硬条件 unknown → unverified。
- 硬条件全部 pass → eligible。

eligible 与 unverified 分开呈现、分别排序。不能为凑够 5 套，把 unknown 归入已验证推荐。没有合格结果时说明数据与覆盖限制，再提出有证据的调整建议；不自动改用户预算。

### 4.2 单一就近偏好

若唯一软偏好是地点距离，对已知距离候选按 `distance ASC`；本地分数采用严格单调函数，因此产生相同顺序。相同距离按租金、房源 ID 稳定打破并列。坐标缺失不是 0 米，未知距离排在已知候选之后。

例：预算 ≤2500 时，2400/月且 600m 的 A 排在 2200/月且 1800m 的 B 前；2600/月且 100m 的 C 先被预算硬条件排除，不会靠近得分“救回来”。如果用户明确说价格更重要，则应增加可解释的价格软偏好，而非暗中改变策略。

### 4.3 多个软偏好

当前基线使用 `sum(normalized_weight × utility)`。每条贡献可回溯到对应事实。用户未给权重时默认 1；明确的重要性应保留为可审阅配置。行为兴趣重排仍由队友 B 实现，当前基线没有把收藏自动变成偏好事实。

如果用户说“距离第一，其次价格”，词典序排序比有限权重更准确地表达绝对优先级；这在当前版本还未实现，不应通过随意给巨大权重冒充同等保证。最终 B 可增设受控 ranking_policy，并与 Contract 一起冻结。

### 4.4 规模扩大时的检索

当前 475 条样本可完整核查，避免错误截断。完整数据或更大候选池可由 B 在 PostgreSQL/PostGIS 建空间索引，结合硬条件作索引检索和 KNN；软偏好不随便塞进 WHERE。若采用候选上限或近邻扩展，必须记录检索覆盖和截断，必要时继续扩展，不能把“本轮没召回”说成“全市场没有”。

不建议仅把地名嵌入向量库后按相似度挑房：语义相似不等于空间相近，也不能证明预算、区域包含或交通路线。

188/613 是所下载站点出口文件的有效覆盖，**不等于宣称覆盖所有未来站、所有出入口或所有新加坡地址**。188 按 MRT/LRT 制式分别计条目，同名换乘站不代表两个独立物理地点；ID 分别使用 `LTA:MRT:*`、`LTA:LRT:*`，避免合并后覆盖出口。道路、楼栋、小区、非标准街区还需持续扩充目录或接入地理编码服务。OneMap 提供搜索及路线 API，但其服务需注册及相应认证；本次没有假装已部署无凭证的实时 OneMap 地理编码。参见 [OneMap 官方文档](https://www.onemap.gov.sg/apidocs/)。

URA 使用的是公开 MP2019 边界版本，不能标成实时行政边界。数据更新时重新下载、校验并回归；不能仅改日期或手改坐标。

## 6. “金文泰”究竟如何解析

```text
金文泰 / Clementi / 克莱门特 / 金文台
  -> PlanningArea
  -> URA:AREA:CLEMENTI
  -> 官方区域多边形

Clementi MRT / ClementiMRT / 金文泰地铁站 / 克莱门特MRT
  -> MRTStation
  -> LTA:MRT:CLEMENTI
  -> 该站已收录出口点集合
```

区域语义：房源点在区域内时距离=0；区域外取到边界的最近地表直线距离。这避免把位于金文泰区内、但离 MRT 稍远的房源误说成“不在金文泰附近”。区内并列时按并列规则排序，不伪造区内各房源到区域的不同距离。

站点语义：计算到每个已收录出口的距离，取最小值，不用出口均值坐标冒充真实入口。区域和站点 refinement 通过稳定 ID 区分；“就是 Clementi MRT”会替换同名的旧区域参考，保留其他无关偏好。真正多义或目录没有的名称才询问，优先给已查到的可选项，不让用户自己调查地标。

区域距离使用 Turf 的 geodesic 多边形距离并将区内负值归为 0，处理多多边形及洞；站点使用球面 haversine。参见 [Turf pointToPolygonDistance](https://turfjs.org/docs/api/pointToPolygonDistance)。均不代表路网距离或公交时间。

## 7. 如何进入数据库和 KG 查询

工作链：`原话 → 受控地名/类型解析 → 稳定地点 ID → SQL 属性候选 → 地图/区域事实 → 硬条件分组 → 组内就近排序 → 带证据解释`。

现有只读 Data API 仍从 PostgreSQL 提供权威房源属性；原 Neo4j 仍保留 OSM 与校园证据。本次在 **7475 的隔离样本图** 新增 GeoArea/GeoRegion/GeoStation/GeoExit，保留各自官方数据版本，不改完整快照图，也不混同原来的邮区 IN_DISTRICT。

已实际投影：55 个区域、5 个大区、188 个站点、613 个出口；593 条样本房源区域归属关系。稳定 ID 可直接参数化查询，例如：

```cypher
// 区域内的房源；不是“附近”的唯一召回范围。
MATCH (l:Listing)-[:IN_PLANNING_AREA]->
      (a:GeoArea {location_id:$area_id})
RETURN l.listing_id, a.name;
```

`area_id='URA:AREA:CLEMENTI'` 来自目录，不由模型拼接用户文本成 Cypher。附近查询还要保留区外候选并计算距离，不能把这条“区内查询”当作无半径 nearby 的完整检索。

```cypher
// 同一站多个官方出口取最近值；可再加明确的3000m条件。
MATCH (s:GeoStation {location_id:$station_id})<-[:EXIT_OF]-(e:GeoExit)
MATCH (l:Listing)
WHERE l.position IS NOT NULL
WITH l, min(point.distance(l.position,e.position)) AS distance_m
RETURN l.listing_id, distance_m
ORDER BY distance_m;
```

目录查询接口已提供：`GET /api/locations/catalog`；单个实体及来源：`GET /api/locations/URA:AREA:CLEMENTI` 或 `/api/locations/LTA:MRT:CLEMENTI`。它们只暴露公开地理数据，不暴露用户会话。B 可使用相同目录 ID，不能拿 LTA/URA ID 去原 OSM Place 表中硬匹配而得到空结果。

## 8. 实际验收与维护

已通过：55 区和 5 大区的中英名称逐一解析；区域与站点类型区分；中文/阿拉伯公里转换；无阈值 soft 距离不减少候选数；归一分在任意距离严格单调；独立 SQL 与官方出口坐标复算前五名；公交补充保留原 30min。完整 TypeScript 测试为 48 项通过，7 项 FastAPI 测试通过。原未知家具/卫浴/路线条件仍为未知，不为了产生推荐而放松。

用户原句目前产生 192 套符合已知预算、但独立卫浴及通勤仍需核实的候选；补 MRT 3km 后为 161 套。它们不是 192/161 套已验证全条件匹配。实际数字仅针对当前安装的历史样本。证据见 [真实业务回归](../evaluation/reports/intake-regression.json)、[KG 投影报告](../evaluation/reports/geo-projection.json) 和 [完整测试日志](../evaluation/reports/typescript-final.txt)。

维护入口：`scripts/sync_locations.py` 下载官方快照；`scripts/project-locations.ts` 仅同步隔离样本 KG；`LocationService` 校验源哈希并提供名称/ID解析。别名表调整应补歧义和类型回归；业务阈值、评分政策、数据版本分开管理。目录会扩充，尚未覆盖的街道/地址不能由 LLM 造坐标补齐。
