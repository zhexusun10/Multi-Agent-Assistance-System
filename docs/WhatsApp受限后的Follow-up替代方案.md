# WhatsApp 受限后的 Follow-up 替代方案

核对日期：2026-10-20。本文为待实施方案，不代表下面的新接入方式已写入代码或完成真实发送验收。

## 当前结论

本项目的 Meta 测试 WhatsApp 业务账户返回 `131031 Business Account locked`。账户详情明确要求完成业务主体验证。管理员 passkey 和广告受信任域名设置不能替代该项主体验证。

实现“通过 WhatsApp 联系经纪人”并不只有平台 Cloud API 一种方式。建议先新增官方 Click to Chat 接入，保留 Cloud API，另把 Twilio 测试环境列为需要账号实测的可选接入。

## 两种替代方式

| 项目 | 官方 Click to Chat | Twilio WhatsApp 测试环境 |
| --- | --- | --- |
| 发送身份 | 用户在 WhatsApp 中登录的账号 | Twilio 提供的测试发送号码 |
| 是否要求本项目取得 Meta WABA | 不需要 | 传统 Sandbox 文档明确不需要自备 WABA 或注册发送号码 |
| 发送动作 | 系统起草，用户在 WhatsApp 中点击发送 | 条件满足后由服务器调用 API |
| 真实经纪人 | 知道正确号码且对方使用 WhatsApp 即可打开聊天，仍须用户确认收件人 | 接收方须加入测试环境；新版试用还有收件人验证限制 |
| 自动取得回复和回执 | 链接不提供此能力，需用户录入回复 | 文档支持来信 webhook 与状态回调，仍需实际配置验收 |
| 当前项目状态 | 尚未实现 | 尚未实现 |

传统 Twilio Sandbox 文档：<https://www.twilio.com/docs/whatsapp/sandbox>

### 必须区分两种 Twilio 环境

传统 Sandbox 允许已加入的接收方在 24 小时用户来信窗口内接收自由文本；主动联系或窗口外使用预设模板。加入会话有有效期，需要按控制台要求重新加入。它仅用于测试。

新版 Try out WhatsApp 文档则明确限制试用发送请求：`ContentSid` 必填，须使用控制台提供的预设模板，不能据此承诺任意协商草稿可发送。传统 Sandbox 文档也明确提示：旧 Sandbox 只在 legacy Console 配置，新版试用使用不同入口。

因此，不能把“注册一个免费 Twilio 账号”直接等同于“完整的自动收发已可用”。需要先实测账号提供哪种环境、是否接受自定义正文以及是否需要升级或付费。正式生产发送也不能把 Sandbox 当作业务验证的替代。

## 推荐先实施的真实联系流程

1. 用户从当前推荐或待核实候选中选择房源，进入已有跟进草稿。
2. 展示历史经纪人姓名、电话、机构和挂牌链接；用户核对实际联系号码。历史号码和链接不能证明当前经纪人身份或 WhatsApp 账号存在。
3. Agent 生成草稿，包含房源链接、租金意向、入住和租期诉求、候选看房时间以及需要核实的硬条件。
4. 用户编辑协商内容并审核最终正文、收件人和时间。
5. 点击“打开 WhatsApp 并带入草稿”，通过 `https://wa.me/<国际格式纯数字号码>?text=<URL编码后的正文>` 打开聊天。
6. 用户在 WhatsApp 中检查收件人和正文并点击发送；第一次打开可能需要按 WhatsApp 自身提示登录或关联设备。
7. 回到工作台点击“我已在 WhatsApp 发送”，系统记录用户声明及其关联的草稿修订。
8. 经纪人回复后，用户点击“录入经纪人回复”，粘贴相关回复并确认房源和联系人。
9. Agent 整理对方报价、可租情况、卫浴说明和看房时段，生成待确认的下一步建议或下一份回复草稿。
10. 双方明确同意后，由用户记录确认依据；再更新看房日历、导出 ICS，并设置提醒。
11. 日总结包含原始草稿、用户录入的回复、证据来源、未核实事项和后续任务。

该流程使用真实 WhatsApp 联系人，不是本地模拟发送；但最后发送和录入外部回复由用户完成。它改变了原先“平台账号代发”的发送身份，产品文案需要明确说明。

## 工程约束

### 外部跳转和发送状态必须分开

建议新增独立的 `handoff_status`：

- `LINK_ISSUED`：已生成用户请求的跳转链接，不证明成功打开 App。
- `USER_REPORTED_SENT`：用户声明已发送；无平台送达证明。
- `USER_REPORTED_REPLY`：用户录入回复；无平台来信签名证明。

保留 `delivery_status` 给真实 API 回执。生成或点击链接均不能写成 `ACCEPTED`、`DELIVERED`、`READ`。手动记录不能创建平台消息 ID，也不能开启 Cloud API 的服务端 24 小时回复窗口。

### 每次联系绑定审核过的内容

链接应从服务端当前动作生成，检查所有者、当前房源、需求版本、修订和审批哈希。编辑正文或收件人后旧审批失效。重复打开不是自动重发，但要保留用户发起记录；界面提示用户核对是否已经发送。

号码使用现有国际格式规范，URL 固定为官方 `wa.me`，正文使用标准 URL 编码。提供复制正文作为长文本、浏览器或 App 跳转不兼容时的备用方式。不能将链接返回结果解释为号码存在性验证。

### 用户录入回复的来源必须可追踪

记录 `source=user_provided`、操作者、录入时间、用户提供的回复时间、联系人、房源、动作和原文。模型抽取结果另存为待确认建议，不改写原始回复，也不直接覆盖爬取数据中的事实。

外部回复属于业务数据，不得作为系统指令执行。模型提出议价、看房改期等建议前，继续检查用户的预算和其他硬条件。

“经纪人表示有独立卫浴”应显示为用户录入的经纪人陈述，不能伪装成原数据库已证实。对不明确日期或同一句涉及多个房源的回复，必须先确认关联，不能自动认定预约成功。

### 看房确认和提醒沿用现有业务规则

候选时段保持待确认；用户明确记录客户与经纪人双方同意且提供依据后才确认。全部时间按 Asia/Singapore 显示。待核实房源可咨询和约看，但未知要求持续显示。

现有提醒是应用内任务，应用运行时扫描到期，不承诺退出应用后继续通知，也不因 WhatsApp 链接打开而自动发送第二条消息。

## 现有代码可复用范围

- `src/domain/actions.ts`：草稿、修订、审核、候选看房、双方确认。
- `src/domain/followup.ts`：时间线、提醒、日历和日总结；需要增加用户声明和回复录入入口。
- `src/integrations/messaging.ts`：当前只有 Meta Cloud API 和 Telegram Bot；建议把 WhatsApp 接入方式独立为适配器。
- `src/server.ts`、`api/main.py`：增加受所有者鉴权保护的跳转与手动记录接口。
- `frontend/followup.js`：增加打开 WhatsApp、复制正文、声明发送、录入回复及确认抽取建议的界面。

不能只增加一个链接按钮，却仍用“已送达”“自动收到回复”的旧文案展示整个工作流。

## 验收要求

1. 无 Meta 凭证时，审核后的真实草稿仍能生成正确的官方跳转链接。
2. 收件号码或正文变化后，不能沿用旧审批生成链接。
3. 带中文、换行、`&`、`?` 的正文解码后与审核正文一致。
4. 生成链接不标记已发送，用户声明发送不标记已送达。
5. 用户录入回复只进入所属用户、指定联系人及动作；来源标签进入时间线和总结。
6. 卫浴、租金等回复抽取结果需要核对；不自动当作数据库事实。
7. 发送咨询或对方单方面提出时段不能直接确认看房；双方同意才可确认。
8. 提醒、下一次草稿、看房日历及日总结形成连续流程。
9. App 是否实际打开、正文是否预填和真实消息是否发送，需要用户设备验收；不能用单元测试或页面跳转成功冒充真实送达。

## 可选的自动收发演示

如果需要展示平台自动接收 WhatsApp 回复，可让组员扮演经纪人加入经实际核查可用的 Twilio Sandbox。先完成账号能力预检，再新增 Twilio 适配器及来信、状态回调验签。

不同 provider 的发送号码、消息 ID 和会话窗口必须隔离；不能把 Meta 来信记录、用户手动录入或另一个 Twilio 账号的来信用于开放当前 provider 的自由文本发送窗口。测试环境支持的功能、费用与生产要求应单独标注。
