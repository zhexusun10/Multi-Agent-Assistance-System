# 租房需求语义、字段覆盖与业务结果验收

> 历史记录：本文描述旧版规则优先提取及当时120条话术审计。当前生产实现已改为LLM优先，见[需求提取LLM优先实现与验收](需求提取LLM优先_实现与验收.md)。旧规则测试不能作为当前真实模型理解能力的证明。

日期：2026-10-19。部署：当前本机历史样本，475 条 RENT。范围：周树晖负责的 A/C/D、编排、工具和前端，以及用于联调的本地推荐基线；不替代崔同学的最终 Recommendation Agent。

## 1. “独立卫浴”究竟是匹配问题还是缺数据

已经直接查询 PostgreSQL 的 `information_schema.columns`、租赁字段覆盖、实际枚举及 raw JSON 填充情况。结论不是猜测：

- 实际 `properties` 有 56 列，含 `bedrooms`、`bathrooms`，**没有 `amenities`、`private_bathroom` 或 `description` 列**。
- 475 条租赁中，475 条有卫浴数量，465 条有卧室数量；其中 192 条的源卧室值为 0，不能据此断言是 studio 或整租。
- 475 条租赁的 `raw_json` 全部为空。标题主要是项目/地址，唯一涉及房型的标题混合写了 master 和 common room，不能据此证明指定出租房间带独卫。
- 因此，当前快照不能恢复独立卫浴或专用使用权事实。不会把 `bathrooms=1`、`bedrooms=1`、主卧、照片、平台认证或抓取成功当作独卫证据。

`amenities eq private_bathroom` 是 Contract V1 中表达用户设施诉求的**抽象条件**，不是在 PostgreSQL 上查一列同名字符串。原实现的 `FIELD_RULES.amenities.unsupported=true` 表示当前能力未覆盖，它会直接得到 unknown，并非因为中文“独立卫浴”没有与英文字符串做模糊匹配。不能只把 unsupported 改成 false，让数据库中不存在的事实变成通过。

这不代表旧实现没有问题：户型简称、口语、比较符、否定和模型合并均发现了真实缺陷，已独立修复。页面也不再显示“amenities 等于独立卫浴”，而显示“必须 · 独立卫浴（专用，不与他人共用）”，并明确说明缺少哪类证据。

原始审计见 [rental-data-audit.json](../evaluation/reports/rental-data-audit.json)。它只有汇总与 schema，不导出电话、房号或 raw JSON 内容。

## 2. schema 存在与样本可用是两回事

| 字段或能力 | 当前租赁样本实际覆盖 | 处理 |
| --- | ---: | --- |
| 月租、币种、卫浴数量、房型、邮区、邮编 | 475/475 | 用有效记录核验；数量不证明出租范围或专用权 |
| 卧室数量 | 465/475 | 缺失为 unknown，保留源值 0，不猜 studio |
| 室内面积 | 282/475 | 有值计算，无值 unknown；平方米确定换算成 sqft |
| 土地面积、建成年份、市场区域编码、产权类别 | 0/475 | 列存在但当前全空，不表示条件未满足 |
| 平台 MRT 距离、平台 MRT 步行分钟 | 0/475 | 能抽取诉求，但当前无记录可核验 |
| 独卫、家具、整租/单间、租期、入住日、可做饭等 | 无对应可核验字段 | 保留条件，说明数据未收录 |
| 指定目的地的真实公交通勤 | 未接路线服务 | 说明路线工具未接入，不用直线距离代替 |
| 当前可租 | 历史快照无法证明 | 独立标注，需实时信息或人工核实 |

特别纠正：仓库 `data/README.md` 定义 `region_code` 为 **CCR/RCR/OCR**。URA 的五个规划大区通过地理实体与多边形处理，不能编出 NER/NR 等代码后拿去匹配房源列。来源字段缺失时也不能冒称已经从地理位置补齐原始市场分类。

## 3. 具体语义策略

| 表述 | 解释 |
| --- | --- |
| 1B1B、2BR2BA、一室一卫、两房一厅一卫 | 明确的卧室数和卫浴数，均用 eq；不附加独卫或整租 |
| 至少两房、最多三间卧室 | 分别为 gte 2、lte 3；上下限冲突先澄清 |
| 裸“两房” | 询问至少还是恰好，保留已有条件 |
| HDB 3-room 等型号 | 不直接视为三间卧室；型号与实际卧室数分别确认 |
| 主卧/普通房 | 表达房间租赁；主卧不自动带独卫 |
| 不和房东同住 | 单独保留诉求，不推断整租 |
| 预算三千、一个月最多两千五、2.5k | 正规化金额；预算明确上限保持 hard |
| 预算 3000，最好租金 2500 内 | 保留 hard 3000 与 soft 2500 两条，不误判预算冲突 |
| 室内/土地面积、上下限/区间 | 字段分别匹配，平方米换算不依赖模型近似值 |
| 公寓/condo/组屋/排屋等 | 按数据目录匹配；公寓泛称可表达 Apartment/Condominium/Walk-up Apartment 并集 |
| 取消独卫、取消某项设施 | 不重加该条件、不删卫浴数量；存在其他设施时只按稳定 criterion_id 删除指定项 |
| 地铁站步行分钟 / 到 NUS 公交通勤 | 平台标注与实际路线是不同字段、不同证据能力 |

房型与 room 标签参考了 [PropertyGuru 实际房间出租栏目](https://www.propertyguru.com.sg/property-for-rent/at-regent-grove-269)，HDB 型号参考 [HDB 官方示例户型](https://assets.hdb.gov.sg/community/lakeside_view/index.html)。实现以当前团队字段契约和实际数据为准，不从某条网上广告推断本地房源事实。

## 4. 120 条测试如何设计及计算

样本见 [rental-cases.ts](../evaluation/rental-cases.ts)，共 120 条人工编写的合成话术，10 组：预算 12、户型/卫浴 18、房型 8、面积/产权 10、地点 10、交通 8、数据能力 16、复合需求 20、多轮修改 10、对抗/否定 8。包含只有一两项的请求，也包含六七项组合、中英文、简称、中文金额、正式表述和口语。

标签独立填写字段、比较符、值、单位、硬软属性、目标/距离口径、交通方式、删除和是否需要澄清；不从 extractor 输出反向生成“标准答案”。同一语料同时跑规则路径和项目 `.env` 配置的真实 DeepSeek 路径。模型路径评估的是**完整混合抽取系统**，不是裸模型能力。模型前置明确歧义由代码裁决，因此“120 条模型模式评估”不等于每条都必须发出模型请求。

指标：

- **整句完全正确率**：上述语义项全部正确、无额外项，并且澄清/删除/支持范围决定正确才算通过。
- **Slot Precision / Recall / F1**：按完整语义槽匹配，错误比较符、值、单位、硬软属性均计错；数值按 0.01 单位比较。
- **抽取异常数**：格式或语义验证失败，不能作为“待核实”掩盖。
- **澄清与删除准确率**：不应要求填写额外条件，不能越权删除旧条件。
- **实际业务一致性**：另用独立 SQL 对照 eligible/unverified/excluded 数量及实际展示的房源 ID。

### 一条标注纠正与比较口径

初始 R058 错把 north-east region 标成 `region_code=NER`。审计团队数据定义后发现标签错误，最终改为区分规划大区和市场分区的澄清。**修改前后配对指标排除这条，共 119 条**；原始评估报告及 corpus hash 保留，初始语料归档保存，不用新标签美化旧结果。最终 120 条的结果另列。

| 同一批可比较的 119 条 | 修改前规则 | 修改后规则 | 修改前模型模式 | 修改后模型模式 |
| --- | ---: | ---: | ---: | ---: |
| 整句完全正确 | 51/119 | 119/119 | 68/119 | 119/119 |
| 完全正确率 | 42.86% | 100% | 57.14% | 100% |
| Slot Precision | 83.33% | 100% | 80.63% | 100% |
| Slot Recall | 48.39% | 100% | 69.35% | 100% |
| Slot F1 | 61.22% | 100% | 74.57% | 100% |
| 抽取异常 | 0 | 0 | 8 | 0 |

最终修正标签后的 **120/120** 在规则与真实模型模式均通过。原始结果：[before-rules](../evaluation/reports/intake-before-rules.json)、[before-model](../evaluation/reports/intake-before-model.json)、[after-rules](../evaluation/reports/intake-after-rules.json)、[after-model](../evaluation/reports/intake-after-model.json)、[配对比较](../evaluation/reports/intake-comparison.json)。

这些是**用于本次迭代的合成回归集**，包含开发者检查和修正规则的样本。文件中的 development/validation 只是固定分组，两组均已检查，不是盲测；不能宣称真实未知用户表达准确率 100%，也不能代表推荐系统的用户满意度、市场覆盖或成交率。

## 5. 找到的问题及最终代码

1. 旧代码漏掉紧凑户型、中文金额、部分家具、普通房、入住日期后置等常见表达。新增 `src/domain/rental-language.ts` 统一处理。
2. “最多三房”比较符、室内/土地面积、面积上下限和 1B1B 的精确语义错误。按维度处理，不拿一个泛化数值正则套所有字段。
3. “取消独卫”曾删卫浴数量并重加独卫；设施否定曾触发预算冲突。现在先识别明确取消，对设施按值/稳定 ID 定向删除。
4. 模型会将面积换算近似值覆盖代码、把明确户型重新问成至少/恰好、把已知有地住宅说成不支持，或由“无同住屋主”推断整租。确定的字面槽由代码拥有；模型只补充尚未覆盖的维度，提案仍受 schema、原文引用、删除授权和语义检查约束。
5. 模型会生成 pool/cat_allowed/entire_unit 等不同 token。已识别词汇直接采用代码的 canonical 值，保留原 Contract V1 的字段与请求格式。
6. 原页面只说 unknown，未解释原因。新增 `field-capabilities.ts`，区分“数据未收录”“记录值缺失/不可用”“路线工具未接入”“实时状态未核实”，展示自然中文。

模型服务错误不会偷偷转为规则模式，更不会把失败请求说成已得到完整推荐。`LLM_MODE=rules` 仍是明确配置的独立模式。当前运行仍为真实模型模式。

## 6. 真实房源结果及界面验收

另选 25 条不同条件的请求，通过真实 `/api/query` 对话、持久任务、Data API 和推荐全流程执行。SQL oracle 从 PostgreSQL 独立计算三值结果，不导入生产的 `compare` 或 `classify`。逐条核对总评估数、eligible/unverified/excluded 及每套展示房源的分组。

实际结果举例：

| 请求 | 已核验 | 待核实 | 排除 |
| --- | ---: | ---: | ---: |
| 1B1B | 36 | 10 | 429 |
| 1B1B，预算 ≤2500 | 4 | 1 | 470 |
| 土地面积至少 2000 sqft | 0 | 475 | 0 |
| 平台 MRT 步行 ≤10min | 0 | 475 | 0 |
| 预算 3000、1B1B、整租、全家具、租一年、指定入住日 | 0 | 9 | 466 |

添加独立卫浴不会使 1B1B 自动满足专用权：网页先显示 4 套已核验数量匹配与 1 套缺卧室数的候选；添加独卫后 5 套均需核实；取消独卫后恢复原分组。这个“恢复”没有更改预算或卫浴数量。

证据：[25 条业务 oracle](../evaluation/reports/rental-business-oracle.json)、[界面五项验证](../evaluation/reports/rental-browser.json)、[1B1B 界面](../evaluation/screenshots/07-layout-1b1b.png)、[独卫缺证据界面](../evaluation/screenshots/08-private-bathroom-unavailable.png)、[完整测试日志](../evaluation/reports/typescript-rental-final.txt)。原金文泰两轮对话也继续通过浏览器回归。

最终 TypeScript 全量测试 **58 passed、0 failed、0 skipped**，类型检查和构建通过。浏览器本轮 5 项及原截图 3 项均通过，未发现 JavaScript 页面异常。

## 7. 数据层下一步应怎样补齐

不能靠多写几个关键词补出不存在的事实。建议与孙同学冻结补数接口后，再启用核验：

1. **保留可审计原始证据**：抓取当时的设施项、出租范围、房间类型及描述；对白名单文本做个人信息清理，不向模型暴露电话、证照、房号或整份 raw JSON。
2. **拆分业务语义**：`bathrooms` 为数量；`rental_scope` 为整租/房间；房间类型 master/common；`bathroom_access` 区分 attached/shared/private_external/unknown；独用权应有独立断言及引用，不能只凭 attached 或 master 一词认定。
3. **属性记录携带证据**：listing_id、出租对象/房间 scope、规范值、原文片段、source URL、采集时间、抽取方法/版本、核实状态、冲突状态。没有提及不等于 false；互相矛盾时不能选一条乐观事实。
4. **受控衍生与能力发布**：如“所出租主卧带独立卫浴”可作为有出处的历史广告声明；描述其他房间、否定、规划描述、广告泛称应为 unknown。先做标注评估，再让只读 Data API 发布这些事实。
5. **最后接核验器**：有实际数据和已约定证据语义后，再更新 `FIELD_RULES` 能力、observed 提取、响应证据校验和 B 的接口实现。当前不提前启用未知字段，不虚构一批独卫标签。

实际公交耗时需另接路线服务并记录交通方式、出发时段和采集时间；当前可租则需要实时核实渠道。这两类能力不等同于补一列房屋静态属性。

## 8. 复现

在项目根目录执行，模型配置只从本地 `.env` 读取，不把密钥放命令行：

```powershell
node --env-file=.env --import tsx evaluation/audit-rental-data.ts
node --env-file=.env --import tsx evaluation/evaluate-intake.ts --tag=after
node --env-file=.env --import tsx evaluation/evaluate-intake.ts --model --tag=after
.venv\Scripts\python.exe evaluation/compare-intake.py
$env:BUSINESS_LIVE='1'
node --env-file=.env --import tsx --test tests/*.test.ts
.venv\Scripts\python.exe evaluation/rental_browser.py
```

审计脚本只读取隔离历史样本；业务验收在自己的随机会话下保存测试状态。详细限制与当前数据版本仍见 `IMPLEMENTATION.md`，完整快照和队友最终推荐 Agent 没有被本报告冒称已验收。
