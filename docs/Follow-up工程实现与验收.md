# Follow-up Agent 与 External Tools 实现

## 业务入口

房源卡片“联系经纪人”绑定当前 `request_id + requirements_version + listing_id`，可从已核验及待核实候选发起。未知硬条件逐条进入核实问题和证据上下文；明确不符合硬条件的候选不能通过该入口跟进。

后续流程是：选择房源 → 生成草稿 → 补充渠道和协商诉求 → 选择候选看房时段 → 保存新修订 → 审核实际正文 → 批准 → 模拟执行或排队真实发送 → 平台结果/回信 → 双方确认看房 → 跟进提醒 → 当天会话文档。

消息从应用的业务号码或机器人账号发出。联系人线索接口只在当前用户拥有的动作中读取所选房源的公开经纪人姓名、机构、电话和挂牌链接，数据库连接为只读；通用推荐数据 API 不扩大电话白名单。历史电话号码不能证明 WhatsApp 已开通，不能转换为 Telegram chat_id。明确核实过的渠道只在同一用户、同一房源范围复用，并再次确认身份和许可。

## 代码边界

| 文件 | 职责 |
|---|---|
| `src/domain/actions.ts` | 选房有效性、修订和内容哈希、审批、日历冲突、模拟执行、双方确认；正文包含协商意向和候选时段 |
| `src/domain/followup.ts` | 数据库发送队列、一次提交、回执/来信、轮询游标、独立跟进任务、日历查询和日总结 |
| `src/integrations/messaging.ts` | 固定官方 HTTPS 端点；WhatsApp 文本/获批模板，Telegram 文本，错误分类与平台限制 |
| `migrations/002-followup.sql` | 队列、回执去重、动作时间线、来信、提醒、完整对话日志及文档类型 |
| `src/server.ts`、`api/main.py` | 所有者鉴权、受控联系人线索、业务接口；原始正文 webhook 转发及验签 |
| `frontend/followup.js` | 渠道与模板表单、草稿、审核、月历、提醒、时间线、ICS、日总结 |
| `api/webhook_gateway.py` | 可选本机隧道入口，仅开放消息 webhook，按原始字节转发，签名由图服务验证 |
| `skills/salesperson-followup/SKILL.md` | D Agent 职责与边界；模型没有真实发送权限 |

发送队列中的正文与当前动作内容哈希绑定。用户修订正文、联系人、模板、协商内容或时段后，旧审批失效。执行先创建唯一执行键和持久队列记录并提交事务，工作进程再次检查当前搜索版本，再标记 SENDING 后调用官方平台。HTTP 不自动重试、不跟随重定向。重复点击同一修订不会第二次提交。

数据库事务无法与外部平台组成原子事务，因此不承诺“恰好一次送达”。网络超时或 SENDING 中断超过60秒标记 UNKNOWN，禁止自动重发。平台明确拒绝为 FAILED；成功返回消息ID为 ACCEPTED。WhatsApp 回执按单调状态推进，重复和乱序回执不重复显示、不把 READ 降级为 DELIVERED。先到的回执暂存，获得消息ID后重新关联。

Telegram webhook 使用 secret header；WhatsApp 使用原始正文 HMAC。来信优先匹配回复消息ID及联系人，缺少回复ID时只能匹配全局唯一动作，避免跨会话泄漏。来信作为外部文本展示，不作为 Agent 指令，不自动执行工具。WhatsApp 回复窗口使用平台原始时间，延迟或重放旧来信不能重开窗口。

`CONFIRMED` 必须由用户记录客户和经纪人都同意，并提供依据。已有历史动作的确认和跟进不因用户继续搜索新房源而消失；未发送动作在新搜索后失效。日历按当前所有者查询多个本地对话，按 Asia/Singapore 显示。查看未来日期不会假定可租或经纪人有空，重叠时段在执行时拦截。模拟确认导出 ICS 仍保持 TENTATIVE，并标注模拟。

## 跟进与文档

独立 `followup_tasks` 可在发送前后创建、改期、完成、取消，使用 revision 防止并发覆盖。等待回复任务收到明确关联来信后完成；看房提醒不因此取消。扫描器每15秒产生应用内到期消息，唯一事件键防止重复；不自动发第二条外部消息。旧动作的 `next_followup_at` 保留兼容，新增 UI 使用独立任务。

日总结按服务器真实日期及新加坡时区筛选当天对话和动作事件，包含来信原文、协商诉求、未核实事项、下一步提醒。需求和动作是生成时快照，有明确标签。完整对话从本次升级起单独保存；升级前已因200条上限丢弃的历史不能恢复。HTML 内容转义，下载按所有者鉴权并校验文档哈希。它是可靠的结构化会话记录，当前不使用模型压缩长对话，避免改写协商与回执事实。

## 区域距离说明

`Queenstown / 女皇镇` 是 URA 区域。区域内房源到该区域的距离为0；这不代表到 Queenstown MRT 为0。UI 已改为“位于区域内”，区域内房源的该偏好距离分数相同；区外按到边界的直线距离排序。指定 `Queenstown MRT` 时查询不同站点实体，并按站点出口计算距离。不会为产生不同名次而伪造区域中心距离。

## 验收入口

```powershell
npm run typecheck
$env:BUSINESS_LIVE='1'
node --env-file=.env --import tsx --test tests/*.test.ts
.venv\Scripts\python.exe evaluation/followup_workflow_browser.py
```

执行命令前按现有部署环境填写正确的测试数据库账号；当前本机账户以 `.env` 和原有运维配置为准。测试不会用生产消息令牌发消息：官方适配器使用注入的假 HTTP 响应，队列验收使用独立假凭证和合成联系人。真实数据库、现有房源检索与网页由本机服务验证。真实平台收发需要另行按[申请配置指南](WhatsApp与Telegram申请配置指南.md)验收。

核心断言覆盖：未审批不能提交、修改使审批失效、重复点击一次提交、正文包含协商和时间、模板与预览一致、窗口/凭证/许可拦截、超时不重发、发送前搜索失效、Webhook 签名/去重/乱序、回信只完成等回复任务、发送后提醒可改期、日历确认独立、日总结原文与HTML转义、会话访问隔离。最终结果见 `evaluation/reports/followup-delivery-business.json`、`followup-workflow-browser.json` 和 `typescript-followup-v1.2.txt`。

补充：首次配置教程提供了 `127.0.0.1:8011` 的可选 webhook 辅助入口，供临时 HTTPS 隧道使用，不开放工作台或业务数据路由。`tests/test_webhook_gateway.py` 的6项新检查与现有API的7项检查合计13项通过，覆盖原始字节/签名头、验证挑战、路径限制、大小限制与上游故障。教程中的临时隧道由用户手工启动，本轮没有创建公网隧道或使用真实平台凭证。
