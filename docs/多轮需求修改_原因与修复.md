# 多轮需求修改：原因与修复

更新日期：2026-10-22。

用户截图中的“需求理解暂未完成”发生在 Requirement Agent 的独立语义复核环节，尚未调用 Recommendation；与上一轮推荐空排名循环是两个问题。

## 故障经过

截图原话：

> 那我修改要求，我要租裕廊东附近5公里内的房子，预算在2500新币每月，房子附近1公里内最好有MRT或公交站，

这条会话原来还保存着一室一卫要求。实际错误记录显示：复核器把旧条件的等价更新误认为删除要求，三次纠错后仍拒绝，因此本轮停在需求阶段。原始错误和旧需求见 [故障记录](../evaluation/reports/requirement-update-failure-before.json)。

回放发现两个具体原因：

1. 复核器只看到原始增删列表，不了解地点解析、按相同目标更新及最终合并的语义。它担心同一交通条件会重复，要求先删除；下一次又把删除旧记录误判为取消用户的要求。
2. “越近越好”排序偏好的内部评分尺度为1000米。复核器把该数字误认成新增的一公里范围，要求删除本来合法的就近偏好。即使加入文字解释，首次提取的真实流程仍能触发此错误；对应记录保留在 [首次流程失败跟踪](../evaluation/reports/requirement-update-workflow-traces-before-v6.json)。

因此，仅增加重试次数或让用户重问不能解决根因。

## 当前执行方式

用户原话与旧需求 → 两条相关示例 → 模型提交严格结构 → 结构、单位、枚举和原文引用校验 → 真实地点解析 → 计算正式保存前的完整需求预览 → 独立模型语义复核 → 通过后提交需求 → 原生推荐 → 自然语言解释。

- 复核器检查最终实际生效的条件，区分“删除旧记录再重建”和“真正取消要求”。不再猜测地点别名或交通联合条件是否会重复。
- 评分参数转换为明确的语义视图：就近偏好表示“仅用于排序、没有距离门槛”，不把1000米评分尺度传成用户限制。原始参数、权重及排序算法保持不变，原始完整条件保留在后台跟踪和实际推荐请求中。明确的一公里交通范围及所有硬范围仍按原值检查。
- 明确规定“修改要求”是增量修改。未明确取消的旧条件保留；相同条件按同一目标更新；明确取消、替换地点和清空旧条件按模型理解后的变更处理。
- 每次尝试保存模型提案、完整需求预览、复核结论、错误与耗时。拒绝的草案不写入正式需求，也不进入推荐。
- 保留严格 Schema、原文引用、有界纠错和独立复核，没有改成关键词提取或遇错直接放行。

在回归中另修正了一个不合理澄清：旧需求为空时，不能因为示例提到通勤，就反问用户是否取消“之前的通勤条件”。已加入同字段“只要某市场分区、其他不要”的示例。

## 同一流程中发现的解释用词

真实页面检查发现：用户要求1B1B，解释示例却把“卫生间数量待确认”带成了“独卫待确认”。数量和专用使用权不能等同。

已在 `src/agents/explanation/evidence.ts` 增加数量与使用权分离的事实说明，`generator.ts` 选择数量专用示例，`few-shot.ts` 增加对应例句，`prompt.ts` 同时约束生成器和复核器。扩充的 `evaluation/explanation-cases.ts` 单独验证该场景，不把一室一卫解释为专用卫浴。

## 用户可见行为与尚未接通的证据

重新发送截图中的修改要求即可处理。只省略1B1B不会自动清空旧条件；明确说“不用1B1B了，卧室和卫生间数量都不作要求”才取消两项数量要求，或明确重新开始。

裕廊东区域、交通站点及卫浴字段在原生推荐侧的接入边界与本次提取修复不同。缺少推荐证据的选项仍显示待确认，不能据流程成功认定全部条件满足。本次没有丢弃这些要求，也没有借用旧算法补排。
