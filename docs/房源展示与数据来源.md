# 房源资料展示

桌面页面使用约35%的对话区、65%的推荐与跟进区；手机页面上下排列。

每张房源卡片先显示价格、用户条件匹配标注和逐项证据，再展示房源本身的资料。资料不以用户有没有提过该条件为前提：

- 房型、卧室和卫浴数量、室内面积、地址、邮区与邮编、楼层。
- 已收录照片与户型图：轮播、全部照片浏览；按图片内容标识去除缩略图和不同尺寸的重复链接。
- 挂牌中的MRT距离、步行时间（如已收录），与知识图谱中已收录的学校、超市、公园、商场、市场、图书馆等周边地点。
- 展开后可看建成年份、产权、土地面积、经纪人和公司、挂牌日期与数据更新时间。

卫浴数量不代表独立使用权；卧室原始值0不直接解释为单间、整租或开间。家具、空调、可做饭、宠物政策等没有结构化记录时明确提示需询问经纪人。照片只展示已保存的来源链接，不据此推断设施。

## 数据与排序

`GET /api/listings/{listing_id}/presentation?session_id=…&source_request_id=…` 只允许读取当前用户、当前推荐列表中的房源。服务调用既有数据 API 的详情、照片与 Neo4j context 接口，再做展示字段白名单、图片去重和距离语义整理。

这属于展示层补充，不向 Recommendation Contract V1 增加必填字段，不改要求、硬条件判定、软偏好排序、评分或证据。补充信息失败时保留已有推荐与条件核查，提供重试，不把失败说成“没有设施”。

- 详情来自 PostgreSQL 历史房源表。
- 照片来自 `property_images`，只在浏览器加载已记录的 PropertyGuru CDN 地址；失败有提示，可继续切换。
- 周边信息来自 Neo4j 关系；OSM距离标为直线距离，采集半径和覆盖边界单独注明。挂牌MRT标注与OSM距离分别显示，不冒充真实路线。

## 看房消息

跟进卡片直接显示和复制框一致的完整消息，例如“我想在2026年10月21日（周三）3:05 PM–6:05 PM（新加坡时间）去看房，请问你方便吗？”。不在正文后再拼接“候选看房时间：”字段。双方是否同意仍由单独的状态和确认记录管理。

## 验收

`tests/listing-presentation.test.ts` 检查字段、图片去重与安全地址、未知值和部分失败。

`tests/listing-presentation-live.test.ts` 使用真实数据库及“新国大5公里、月租2000、越近越好”搜索，独立对照每条房源的SQL字段，核对获取补充资料前后推荐不变，并验证会话权限与版本边界。

`scripts/test_listing_presentation_ui.py` 检查真实照片加载、轮播和大图、照片失败回退、桌面35/65布局和手机布局，以及口语化看房时段与复制内容一致。

验收结果和截图保存在 `evaluation/reports/listing-presentation-*`。测试会话独立，不向经纪人发送任何消息。
## 卡片折叠

每张房源卡片底部提供收起 / 展开箭头。收起后仅显示房源名称与展开按钮，照片、价格、匹配证据和跟进按钮一起隐藏；展开后恢复原内容。各卡片独立控制，同一会话、同一推荐版本下，工作台刷新和切换页签会保留选择，新搜索结果默认展开。键盘 Enter / 空格也可操作；手机端采用相同规则。
