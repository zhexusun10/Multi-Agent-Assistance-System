# 房源详情、真实浏览反馈与按需推荐

实现日期：2026-10-21。以本文件描述当前实现；此前《真实浏览反馈与自动重排设计方案》为设计讨论记录。

## 用户如何使用

1. 正常提出找房需求，得到本轮推荐。
2. 点击卡片“展开详情”，在主工作区查看这套房的照片、户型、已知属性、周边和实际匹配距离。左侧对话保留。
3. 点击“返回推荐列表”继续比较其他房源。本轮顺序、滚动位置和编号选择恢复，不因浏览改变。
4. 系统自动保存有效详情浏览；无需输入秒数。下次说“按当前需求重新推荐”，或修改预算等条件后，系统自动携带合格兴趣反馈。

浏览、退出详情、停止滚动、收藏、解释和跟进操作均不会自行启动推荐。界面不显示手动样例时长录入按钮。

## 页面实现

- `frontend/property-detail-view.js`：独立详情主视图，固定来源推荐 ID、房源 ID、需求版本和活动搜索；返回时恢复列表位置。新搜索使旧来源失效时退出旧详情，不把旧条件冒充当前条件。
- `frontend/listing-details.js`：列表不展示照片；详情统一展示已知资料、完整图库、户型和周边。
- `frontend/app.js`、`frontend/index.html`、`frontend/style.css`：桌面对话约330px，其余主区域用于详情；手机上下布局与详情滚动。没有新增前端框架。
- 浏览采集在后台执行，不展示计时、评分、数据覆盖或内部证据 JSON；实现状态只供自动验收读取。
- `frontend/listing-navigator.js` 提供编号跳转与滚动高亮；`frontend/property-presentation.js` 统一列表、详情的月租和实际距离呈现。

## 有效时长口径

`frontend/view-tracker.js` 使用单调时钟 `performance.now()`。详情加载成功、页面可见、有前台焦点、用户活动区域为该详情或其照片子视图时计时。

后台、失焦、聊天输入、系统说明弹窗、草稿和日历操作均暂停。静默30秒暂停；滚轮、触摸或键盘等真实交互可恢复。程序自动滚动聊天记录不会被当成用户活动。桌面使用 `document.hasFocus()`，触摸设备结合页面可见性和窗口前后台事件，避免完全依赖不稳定的移动端焦点实现。

每个连续区间最多约120秒后切为新段。切后台、空闲、返回列表等也结束当前段；恢复时使用新段 ID，避免修改已经提交给推荐的反馈。同一浏览器用户通过服务端25秒租约同时只有一个活动计时段。心跳10秒，过期/被替换的租约不补算未确认时间。

浏览器冻结造成超过5秒的计时间隔不直接补算。崩溃后在下次用户推荐请求中封存已过期段，只承认最后确认心跳中的有效时长，不外推到关闭时间。

列表曝光用 `IntersectionObserver`，绑定列表滚动容器，观察摘要区域至少50%可见约1秒；列表曝光不进入原生兴趣时长。

这些规则测量的是有效浏览的保守估计，不能证明用户一直注视屏幕或确实喜欢房子。静默规则可能低估长时间静读；阈值需通过试用评估。

## 持久化、鉴权与重试

迁移文件：`migrations/004-browser-interest.sql`，随 `DomainStore.setup()` 幂等初始化。

| 表 | 用途 |
|---|---|
| `listing_exposures` | 来源推荐、房源、位置和标签页曝光 |
| `listing_view_segments` | 已确认累计时长、序号、段状态、原始来源和质量备注 |
| `browser_reading_leases` | 按用户身份串行计时，避免多标签页重复累计 |
| `browser_behavior_receipts` | 事件 ID 与内容指纹，重复投递返回原确认 |
| `listing_feedback` | 已准备且不可变的完成反馈，以及成功消费标记 |
| `recommendation_calls` 新列 | 本轮反馈水位 `feedback_cutoff` 和 `interest_context` |

API：

- `POST /api/behavior/views`：`exposure` / `begin` / `heartbeat` / `complete`，沿用 Authorization 鉴权。
- `GET /api/behavior/summary?session_id=...`：仅会话归属者可读；返回观察统计，不触发推荐。

服务端从本会话的 `recommendation_calls.response` 校验该房源确实曾被展示。合法历史推荐的延迟事件可入库，其他用户、未知房源、虚构属性、时长倒退、超出真实经过时间的累计值及冲突事件均被拒绝。

客户端 `frontend/behavior-outbox.js` 使用按身份 SHA-256 命名的 IndexedDB 队列。累计包先保存再发送，重试保留同一事件 ID；恢复网络或重开页面后补发。使用带认证头的 fetch/keepalive，不把凭证放入请求体或页面退出 URL。开始计时需要服务端确认，未确认的离线初始打开不编造浏览时长。

## 何时用于推荐

`src/domain/behavior.ts` 的 `INTEREST_POLICY` 是首版集中策略：

- 每套房源跨完成段累计有效时长至少15秒；
- 至少两套不同的、原生允许学习的房源；
- 合格房源总时长至少60秒；计算门槛时每套上限120秒。

这些条件只控制是否将真实浏览转成兴趣输入，不阻止用户搜索，也不是自动刷新条件。证据不足时照常按明确需求推荐。

`prepareBrowserFeedback()` 只在用户请求生成推荐时调用。`src/domain/workflow.ts` 使用该用户操作创建时间作为反馈水位：只读取此前已确认的完成段；本轮进行中才到达的数据留到下一次用户推荐请求。

重新推荐复用已确认需求；修改预算等则先更新需求。原来的意图分类、Requirement/Explanation/Follow-up 路由保持。没有定时重排任务，也不伪造聊天消息。新请求/新需求继续享有过期任务保护。

反馈在 Recommendation 成功返回后才标记已消费；失败和重试保持原请求身份，不能丢失行为。原生自身也会按事件 ID 和完成浏览 ID 去重，因此重试不翻倍。

## 与江山原生模块的边界

真实反馈使用 `source=web_detail`，原来的 `sample` 仍兼容。`src/adapters/native-recommendation.ts` 将有效完成段的毫秒转换为秒，房源属性取自原生此前保存的推荐，不由前端重新提交。

仅有5个原生文件存在明确的契约/来源元数据扩展：

1. `recommendation/contracts/feedback.py`：允许真实来源。
2. `recommendation/contracts/schemas/feedback.schema.json`：对应生成 Schema。
3. `recommendation/contracts/schemas/request.schema.json`：内嵌反馈 Schema。
4. `recommendation/context/manager.py`：档案来源区分真实、样例和混合；时长汇总不变。
5. `recommendation/service.py`：真实来源使用真实浏览估计提示，不伪装为样例。

原版迁移指纹仍在 `contracts/releases/recommendation-upstream-907cfa8.json`；扩展前后指纹在 `contracts/releases/recommendation-web-feedback-extension.json`。导入脚本校验两层清单，并拒绝直接重导入覆盖已实施扩展。

评分、相似度、权重、硬条件、特征停用、工具排序和最终校验核心保持原字节。真实浏览与原样例使用同一算法：时长按房源汇总后最多120秒、对数权重、内容相似度；有显式软偏好时按80%显式/20%隐式融合，只有隐式时使用隐式分。如果明确条件已经停用了全部可推断特征，本轮会如实说明没有使用隐式评分，不因已采集数据就声称兴趣影响了排名。

原生仍只接受此前已验证推荐房源的反馈。待核实候选的浏览事实会保存，但不进入原生学习；独立卫浴等契约能力缺口没有被伪装为已验证。收藏没有被转换成秒数。不保证每次重新推荐都会换房源，结果应由真实评分决定。
