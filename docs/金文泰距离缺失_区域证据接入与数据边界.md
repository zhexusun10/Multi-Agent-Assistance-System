# 金文泰距离缺失：区域证据接入与数据边界

## 归因

用户原要求为金文泰附近、公寓、3000新币以内、恰好1间卧室；卡片新增500–1500 sqft硬条件，保留原预算。地点在补充前后都是`URA:AREA:CLEMENTI`，没有丢失或被其他字段覆盖，也不存在优先级冲突。

实际有两个问题：

1. 应用地点目录、图谱GeoArea和官方区域边界已经存在，但原生地理仓库仅查询`Place`/`NEAR_PLACE`，不查询`GeoLocation`。因此URA目的地一直被判为unresolved，距离证据没有进入评分。前一轮的文字说明不证明那轮已经真正计算了区域距离。
2. 截图中的Estella Gardens、Woodhaven、Carissa Park Condo、The Estuary @ Yishun、Hillview Green，房源SQL的经纬度都为空，Neo4j对应Listing.position也为空、coordinate_status=missing。只有目的地区域边界还不足以算距离，必须同时有房源起点坐标。

补充后符合硬条件的82套中，9套有坐标、73套缺坐标；补充前338套中35套有坐标。不能把未知位置填成0米，也不能把同名车站或区域中心代替区域边界。

## 接入方式

在应用HTTP推荐入口包一层`ApplicationGeographicRepository`。OSM条件直接委托原仓库，结果保持一致。URA/LTA条件先按稳定ID读取已经投影的GeoLocation，再调用只读Node测距桥，复用应用现有地点目录和`distanceToEntity`实现。

- 校验源文件SHA-256、目录版本、图谱目的地ID/名称/版本及结果覆盖；不猜坐标。
- URA规划区或大区：区内距离为0，区外取到区域边界的最近大圆距离。
- LTA站点：取官方文件已记录出口中最近的直线距离，保留MRT/LRT各自身份。
- 缺少房源坐标、未知目的地仍返回有原因的未知；无路线证据时不把直线转换为步行/驾车分钟。
- 证据带源目录、版本、测量方法及快照哈希，交给原来的硬条件比较、显式偏好评分、融合排序和final_gate重读。最终校验仍会重算并检查证据快照；新请求不使用旧缓存分数。

原始`recommendation/repositories/geographic_repository.py`、ranker、metrics、dispatcher、rules和gate均未修改；终端原生入口保持原方式。应用数据适配与推荐公式分离，不在展示阶段另行重排或补造结果。

## 页面及解释

卡片和详情直接显示“位于金文泰区域内”或“距金文泰区域边界N米（直线，更近优先）”；已知距离不再进入待确认。真实缺坐标时写明“到金文泰的距离（缺少房源坐标）”。解释事实和恢复文案使用相同距离及区域口径，不会把0米解释成到地铁站0米。

历史结果不自动替换名单。用户主动重新推荐或修改需求后，新一轮才使用接入后的证据进行原生排序。

## 零付费验证

使用真实SQL、Neo4j及原推荐算法，在隔离进程中分别执行补充前和补充后两个请求；仅测试进程使用scripted控制器，生产仍为live。两个请求的Top5都与独立读取整个硬条件候选池、计算区域距离后得到的次序一致；每套数值和原始proximity公式结果一致。该测试不调用任何LLM。

补充后当前可定位记录中，最近的Windermere到金文泰区域边界约6299.65米；后几套更远。这只代表当前有坐标记录的比较结果，不能声称金文泰附近没有房源，也不能宣称它们都在附近。缺坐标的数据补齐前，数据覆盖限制仍然存在。

Python测试验证原OSM委托、区域内0米/区外距离、缺坐标未知、站点出口距离、步行证据不可用、KG与目录不一致及重复结果拒绝。浏览器使用真实数据回放，验证五张卡片、详情和介绍的距离一致，待确认中不再包含已知距离。报告为`evaluation/reports/official-geography.json`和`official-geography-ui.json`。
