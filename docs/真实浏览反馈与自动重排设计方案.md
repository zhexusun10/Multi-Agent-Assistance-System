# 真实浏览反馈与按需重推荐设计方案

日期：2026-10-21。本文保留设计讨论与修改蓝图；当前已经实施的范围、文件和验收以[真实浏览反馈实现说明](真实浏览反馈_实现与验收.md)为准。按用户最新意见修订：自动采集、用户请求时使用兴趣生成新推荐；不因停止滚动、退出详情或浏览达到某个时长而自行替换列表。文件名保留，方便此前链接继续访问。

## 1. 设计结论和当前基础

采用“简洁列表 + 主工作区房源详情 + 自动有效浏览采集 + 用户请求时融合兴趣 + 本轮列表固定”。左侧找房对话保留；点击卡片的“展开详情”，右侧整个主工作区切换为单套房源详情，不再在列表卡片内部挤出一个小窗口。

用户停止滚动时仍可能在阅读，退出详情时仍可能正在对比，因此不把这些动作视为更新展示的授权。一次推荐结果在本轮浏览中保持固定；只有用户明确要求重新推荐，或修改找房条件并确认后，才执行并展示下一轮结果。首版不做无人请求的后台完整推荐，以免浪费模型调用、推进原生状态或引入无用的待采用结果。

展开详情是更明确的浏览对象选择，但时长只能表示关注线索，不能直接证明喜欢。长时间查看也可能来自困惑、资料复杂或忘记关闭页面。界面设计会影响反馈数据的质量，相关研究可参考 [Shaping Feedback Data in Recommender Systems](https://www.microsoft.com/en-us/research/publication/shaping-feedback-data-in-recommender-systems-with-interventions-based-on-information-foraging-theory/)。点击与停留时长结合的研究可参考 [Reweighting Clicks with Dwell Time in Recommendation](https://arxiv.org/abs/2209.09000)。这些研究支持使用多种观察信号，不提供本项目可以直接照搬的秒数阈值。

已存在的基础：

- `frontend/app.js` 中的“录入浏览样例并重排”按钮，实际会先提交样例，再调用 `sendQuery()` 发起一次推荐。用户不必修改需求，但目前仍需点击这个演示按钮。
- `src/server.ts` 的 `/feedback` 保存事件，当前要求事件引用最新列表。
- `src/adapters/native-recommendation.ts` 只把 `source=sample` 的时长事件传入原生模块。
- 原生 `recommendation/contracts/feedback.py` 也只接受样例来源；`context/manager.py` 完成事件去重、时长汇总；`ranking/ranker.py` 计算兴趣分。
- `src/domain/workflow.ts` 已有任务队列、需求版本和过期任务保护；复用原有用户推荐入口，在请求创建时装载已确认兴趣反馈，不能因浏览行为伪造一条用户聊天消息。

## 2. 详情界面

桌面端保留约 300—360px 的找房对话区，剩余主工作区展示单套房源。宽度根据屏幕适配，不使用覆盖整页的强制浏览器全屏。

详情包含标题和租金、照片与户型图、房型/卧室/卫浴/面积、地址、与用户需求的匹配、证据与未知事项、周边地点、经纪人资料，以及收藏/咨询/看房入口。上半区照片与基本资料并排，下半区按内容分区。照片层属于当前房源详情的子视图。

“返回推荐列表”恢复进入前的列表顺序、滚动位置和卡片折叠状态。详情打开期间保持房源 ID 与来源推荐版本固定。需求被用户修改导致旧推荐失效时，明确提示并停止旧版本兴趣计时，不能继续显示为当前条件已通过。

列表曝光和详情阅读分别记录。列表里看到多个房源，不代表用户同时阅读了多个房源；列表曝光首版不作为原生浏览时长输入。

## 3. 有效浏览时长

只有以下条件同时成立，才累计当前房源的详情阅读时间：

1. 用户主动打开这套房源，基本详情成功显示；加载等待和错误重试不计入。
2. 页面处于 `document.visibilityState === 'visible'`。
3. 桌面浏览器中页面有焦点；失焦时保守暂停。移动端需要独立验证焦点事件，不能把不可靠的焦点判断作为唯一依据。
4. 当前活动区域是房源详情或其照片子视图。左侧对话输入、跟进草稿编辑、看房日历、其他模态框不计入。
5. 未进入长时间无操作状态；首版静默 30 秒后暂停，滚动、键盘、触摸、切换照片等有效交互恢复计时。
6. 同一浏览器、同一用户会话同时只有一个计时标签页。

静默阈值会低估长时间静读，不能称为准确注意力测量。保守采集首先减少后台挂机的误计；阈值需要通过真实试用校准。鼠标停在卡片上和不断移动鼠标都不直接等价于兴趣。

计时使用 `performance.now()` 的单调时钟，按条件改变时切分区间，不按 `setInterval` 实际执行次数累加。切后台、休眠、长任务或浏览器冻结后，无法确认的空档不补算。

列表曝光使用 `IntersectionObserver`，其 `root` 设置为实际列表滚动容器。观察标题/摘要等有固定范围的区域，避免整张长卡片高度大于视窗导致可见比例永远达不到阈值。初始曝光规则为摘要区域可见至少 50%、持续至少 1 秒；记录位置和推荐版本。IntersectionObserver 不能单独判断标签页是否在后台，需结合 [MDN 的可见时间示例](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API/Timing_element_visibility)。

### 3.1 示例

用户阅读房源 A 20 秒，切到其他标签页 60 秒，返回后继续阅读 15 秒，再在聊天区输入 10 秒。A 的有效浏览记录应为 35 秒；后台和聊天时间不算到 A 上。A 与 B 不得并行累计。

### 3.2 采集与兴趣分离

| 观察 | 保存事实 | 首版进入原生时长模型 |
|---|---|---|
| 列表卡片曝光 | 房源、排序位置、曝光时长、版本 | 否 |
| 主动进入详情 | 打开动作、来源版本 | 单独打开动作不作为时长 |
| 有效详情阅读 | 有效时长、暂停原因 | 达到质量门槛且原生允许学习时进入 |
| 图片翻页、展开户型图 | 行为类别和次数 | 作为质量分析依据，不换算额外秒数 |
| 收藏、联系、看房 | 独立业务事件 | 不伪造浏览秒数 |
| 快速返回或关闭 | 真实记录 | 不直接当负反馈 |
| 详情加载失败、后台打开 | 失败或曝光事实 | 不贡献兴趣时长 |

首版维持江山算法的显式/隐式融合公式；不额外增加未经评估的“翻一张照片加十秒”等规则。若以后接入显式喜欢/不喜欢，应定义独立契约，不塞入浏览时长。

## 4. 上报、保存与原生反馈契约

### 4.1 原始浏览记录

新增 `POST /api/behavior/views`，支持开始、心跳、完成三类消息。核心字段：

| 字段 | 用途 |
|---|---|
| `event_id` | 一次上报的幂等 ID |
| `view_session_id` | 一次浏览会话 ID |
| `segment_id` | 可见/活动状态连续区间 ID |
| `sequence` | 防止乱序回写累计值 |
| `session_id` | 当前租房会话；服务端核验归属 |
| `listing_id` | 当前房源；服务端查询属性，不信任前端提交房型和坐标 |
| `source_recommendation_id` | 用户当时看到的不可变推荐版本 |
| `requirements_version` | 当时的需求版本 |
| `source` | 真实采集明确为 `web_detail` |
| `active_duration_ms` | 该段累计有效时长，不能重复求和 |
| `occurred_at` | 客户端时间，仅作辅助 |
| `received_at` | 服务端接收时间，用于边界校验 |
| `end_reason` | 返回列表、隐藏、失焦、空闲、切换会话等 |

初始每 10 秒上报一次小心跳，暂停或退出时立即上报。服务器按会话/段和 sequence 保存累计值，高版本覆盖低版本；重复投递不累加。

原始心跳可以更新，进入推荐的完成反馈必须不可变。每个完成段只生成一次原生事件；后续恢复阅读使用新的段 ID。浏览器崩溃或网络中断时只承认已确认的时长，不从最后心跳无限外推。

使用 IndexedDB 保存未确认的小批量事件，成功确认后删除，重连重试保持同一 ID。现有鉴权使用 Authorization 请求头，常规上报和退出补报使用 `fetch(..., {keepalive:true})`，保持原有认证头；不能直接换成无法设置该认证头的 sendBeacon。keepalive 只提高送达机会，不保证送达，仍需要本地队列和服务器幂等。[MDN 说明](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/sendBeacon)。

服务器检查会话归属、历史推荐中是否确实展示过该房源、累计值单调性、时长与服务端经过时间的合理边界、并发标签页租约和事件大小。浏览器上报不能证明用户实际注视屏幕，校验目标是拒绝明显异常和重复，不宣称能验证心理兴趣。

### 4.2 历史来源与当前接口的调整

现有 `/feedback` 只接受最新推荐。用户明确发起下一轮推荐后，旧详情的延迟上报仍可能合法，因此真实行为接口必须核验“本用户曾被发出的推荐版本”，而非只核验 `latest_request_id`。不能因此允许任意房源 ID 或其他会话的数据。

新增数据表建议：

- `listing_exposures`：谁在什么推荐版本、哪个位置看到过什么。
- `listing_view_segments`：原始时段、累计值、序号、状态和质量标记。
- `interest_feedback_outbox`：不可变、可重试的完成反馈；按段 ID 唯一。
- `recommendation_generations`：本轮依据的需求、反馈版本、来源列表、结果及展示状态。
- 兴趣反馈持久化重试复用 outbox，不新增定时触发推荐的 `interest_refresh_jobs`；用户发起的推荐继续复用已有工作流队列。

反馈只有在推荐调用成功后才确认消费；失败重试使用同一请求和反馈 ID。避免一开始标记已消费，随后模型失败导致行为丢失。

### 4.3 原生契约修订

在 Python 反馈模型、JSON Schema 和 TypeScript 校验中新增真实来源 `web_detail`，保留 `sample` 演示兼容。同步调整 `context/manager.py` 的来源元数据、`service.py` 的样例提示和前端“样例兴趣”文案，真实数据不能仍被标为模拟数据。

保留事件去重、时长汇总、120 秒评分上限、相似度、权重、显式特征优先和最终排序公式。契约修订单独记录与原版差异，不能继续声称扩展后的反馈文件与原版逐字一致。

原生当前只允许反馈引用此前已验证推荐中的房源。全部详情可以记录浏览事实，但待核实候选首版不进入原生兴趣模型；如需支持，须明确扩展可学习集合契约并补充验收，不把待核实项伪装成已验证项。

首版兴趣范围限定在当前租房会话，提供关闭个性化、清除本次兴趣数据的入口；不采集键盘内容、聊天正文、外站浏览或浏览器指纹。

## 5. 用户请求时执行新推荐

浏览行为只触发保存与兴趣反馈准备，不触发 Recommendation Agent。达到采集门槛、冷却结束、停止滚动、退出详情都不能单独启动或展示新推荐。

| 用户行为 | 是否执行下一轮推荐 |
|---|---|
| 展开、关闭、切换房源详情，返回列表对比 | 否，当前结果固定 |
| 停止滚动、长时间阅读、切到其他标签页再回来 | 否 |
| 收藏、查看照片、生成联系草稿、操作看房日历 | 否 |
| 询问知识、要求解释某套房、生成总结 | 否，分别进入原有专用流程 |
| 明确说“按当前条件重新推荐”“结合刚才看的房源再推荐” | 是，复用已确认需求并融合合格兴趣反馈 |
| 修改预算、位置、户型等找房条件 | 新条件确认后执行，融合合格兴趣反馈并保持硬条件优先 |

不要求用户掌握“何时重排”，也不新增必须点击的技术性重排按钮。用户通过正常的找房对话表达下一次推荐意图；系统自动把此前行为作为辅助输入。只重复询问房源细节不能误判为要求新推荐。

兴趣质量与推荐触发分别处理。单次有效详情至少 15 秒；首次使用兴趣可试行至少 2 套不同合格房源、累计至少 60 秒。这些只是可配置、待用户试用校准的兴趣使用门槛，不是界面自动刷新的计时器，也不阻止用户任何一次正常搜索。证据不足时仍执行用户请求，只使用明确条件和原生可用信号。

具体请求流程：

1. 用户提交找房或重新推荐请求时，前端先结算已经结束的有效浏览段并尽力补报；网络补报不得无限阻塞搜索。
2. 服务端创建请求时固定已确认反馈的水位、需求版本和请求 ID；在事务中预留本轮待消费事件。
3. 使用当前明确需求和该水位内的合格反馈调用原生 Recommendation B，再进入 Explanation C。重新推荐不需要让用户重述全部需求。
4. 请求开始后才确认到达的反馈留给下一次用户请求，不导致本轮自动再算一次。
5. 成功后确认消费；失败保持同一请求 ID 重试，反馈不丢失、不重复生效。
6. 多个用户请求继续使用已有队列、幂等和较新需求优先规则。旧请求结果不能覆盖新请求。

取消前版“45 秒新增时长、90 秒冷却、5 秒合并后自动调用推荐”的策略。原生每轮仍执行完整候选池和最终校验，不把前四套局部交换顺序当作完整重推荐。

## 6. 本轮列表固定与下一轮结果发布

新增三个独立概念：

- `requirements_version`：用户明确需求版本，浏览行为不修改它。
- `feedback_version`：已确认兴趣反馈进度。
- `recommendation_generation`：本次展示结果版本。

浏览期间只有反馈版本可以增加，当前推荐版本、排序、卡片位置和详情身份都不随之改变。退出详情恢复的必须是进入前那一版列表，允许用户反复比较 A 和 B。

只有用户明确发起下一轮推荐后才显示“正在按你的条件更新推荐”；计算完成后按该请求正常发布新结果。没有用户推荐请求时，不显示自动更新倒计时，不后台替换，也不以闲置时间判断用户是否读完。

新结果发布时事务检查用户请求、需求版本和反馈水位，防止旧请求覆盖较新请求。需求变更后的历史列表保留历史身份，不能继续冒充满足新条件的当前列表。详情中的原房源不被偷偷换成新排名第一名。

多个标签页的显示和历史访问同样以用户请求及来源版本为依据，不能仅因其中一页停止操作就覆盖另一页正在比较的历史结果。

若新一轮使用了兴趣，可在结果说明中写“本次也参考了你之前浏览的房源”，不宣称已确定用户喜欢哪些属性。即使排名未变，也如实说明；不为了表现个性化而强行换房源。

已保存草稿、历史看房安排和经纪人对话保持绑定原房源及原来源版本，不因为下一轮推荐变化自动撤销或修改。

## 8. 分步交付与验收

1. 实现详情主视图，验收内容完整、返回恢复、照片和跟进入口。
2. 实现浏览采集与持久化，先验证测量，不立即影响用户排序。
3. 扩展真实反馈契约，使用固定行为回放核对原生评分，保留原版算法对照。
4. 在已有用户推荐请求中接入反馈水位、消费确认和失效保护，不新增无人请求的推荐任务。
5. 验证本轮列表固定和下一轮结果正常发布，删除正常用户流程中的手动样例/重排按钮。
6. 进行端到端业务验收和小规模用户试用，根据效果校准阈值。

必须覆盖的验收场景：

- 同屏两张卡片不同时增加兴趣时长；长卡片曝光可正确检测。
- 后台、最小化、聊天输入、草稿编辑、日历和加载失败均暂停计时。
- 静读与空闲边界、休眠、照片子视图、移动端后台恢复有明确记录。
- 断网重试、重复心跳、乱序上报、刷新/BFCache 恢复不重复累计。
- 多标签页同时打开同一房源不会双倍计时。
- 不论是否达到兴趣质量门槛，仅浏览都不启动推荐、不改变当前排序。
- 退出详情、静读、滚动停止和跨房源反复对比时，列表身份、排序和滚动位置保持不变。
- 用户明确重新推荐、修改需求并确认后，自动携带请求开始时已确认的合格反馈；无需手动录入或点技术性重排按钮。
- 解释、知识问答、联系草稿和日历操作不触发新推荐。
- 反馈不足不阻止用户搜索；请求期间新增反馈留到下一次用户请求，不能引起追加刷新。
- 新用户请求压过旧请求，旧结果不回写；当前详情不能被新排名的另一套房源替换。
- 待核实候选不被伪造为原生可学习的已验证推荐。
- 任务失败、服务重启、结果提交失败后反馈仍可恢复；同一完成反馈只生效一次。
- 用固定事件序列独立计算时长权重、四特征相似度和融合分，与原生返回及前四名一致。
- 用户浏览兴趣与硬条件冲突时，硬条件仍完全满足。

测量正确性和兴趣有效性分别评估。固定脚本可检查可计时区间误差、漏报/重报、版本正确性与硬条件合规；兴趣质量需结合用户主动收藏、明确喜欢/不喜欢、咨询/看房选择等结果，比较更新前后 Top-4 偏好命中和列表变动。不能用单元测试全通过证明已经准确理解用户兴趣。

记录推荐位置、曝光与内容完整度用于评估位置偏差和页面复杂度偏差。首版不新增探索分、热度分、负反馈算法或时间衰减；四套内容高度相似时，承认现有行为不足以区分偏好，不夸大个性化能力。

## 9. 简化执行流程

```text
点击展开房源 → 主工作区详情 → 有效计时/暂停 → 完成反馈落库
    → 返回原列表继续比较（排序保持固定）

用户明确重新推荐 / 修改找房条件并确认
    → 固定需求与已确认反馈水位 → 原生推荐 B → 解释 C
    → 发布本次用户请求的新结果
```

用户正常浏览即可完成数据采集；用户发起下一轮找房请求时，系统自动把合格兴趣反馈用于推荐。用户掌握何时请求新结果，系统承担反馈整理、计算和版本一致性。
