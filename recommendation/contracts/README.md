# Recommendation interface v2.0

This package contains requests, requirements, feedback events, the behaviour context, evidence, entity-resolution / pool / selection summaries, status/error fields, state/trace references and a generic response envelope. It imports independently of database, agent and recommendation implementation initialization.

`request.py` is the input boundary: main's orchestrator request contract (`contract_version` `"1.0"`; a 2.0 request body is rejected with `UNSUPPORTED_VERSION`) plus the recommendation-owned `cold_start`. `feedback.py` defines main's incremental `ViewingEvent` (validated, not scored) and `behavior.py` main's `behavior_context` (session-cumulative `listing_view_durations` and saved timed `book_viewing_listings`), which is what the scorer uses. `response.RecommendationResponse[T]` is the generic output envelope and `summary.py` its resolution, pool and selection summaries. The concrete item uses internal `ListingSummary` and `ScoreBreakdown` models and is bound in `recommendation.models.candidate.Response`. `limits.py` holds the shared bounds (`MAX_RESULT_LIMIT` = 10, equal to `recommendation.max_result_limit`).

Language-independent consumers should validate against `schemas/request.schema.json` and `schemas/response.schema.json`. All nested definitions resolve inside those documents. Run `python -m recommendation.schemas --check` to detect drift; omit `--check` to regenerate. Generated schemas use the pinned Pydantic 2.14 minor series. The strict TS mirror is `src/contracts/recommendation-native.ts`.

Use a new request ID for each logical update, a stable conversation ID, a complete requirements snapshot, a monotonically increasing requirements version when changed, and the most recent `state.state_id`. Behaviour-only requests retain the requirements version. `behavior_context` is the orchestrator's complete snapshot as of `as_of` every time (one summary per listing; only `interest_eligible` summaries with seconds > 0 are browsing references; every saved viewing draft is an appointment reference). Nothing is accumulated across requests natively. `cold_start` (`exited`, `exited_pool_key`) is still accepted for compatibility but is ignored by the cold-start decision (recorded as unused in the trace). Durations are page-observed attention estimates (or samples), not click counts. See MIGRATION.md section 0.

Responses use `success`, `needs_clarification`, `no_match`, or `error`. Only success carries verified recommendations (at most `result_limit`, default 10). There is no unverified-candidate list: listings excluded because a hard criterion is unknown are counted in `pool`. Each item reports its display `rank`, its `score_rank` in the full-pool order and its `selection_reason`. `selection.cold_start` reports the `mpd-v1` detector (`detector`, `detector_version`, `candidate_window`, `evaluated_count`, `mean_pairwise_difference`, `threshold`, `pool_key`); stored historical responses may carry the legacy C/B/S shape, which is accepted as stored and never reinterpreted as D. `evidence` holds one entry per (evidence_id, criterion_id) referenced by the returned items. Never treat an error as an empty successful search. `run_sequence` distinguishes feedback-only updates. The orchestrator must discard responses superseded by its latest request.

Examples: [`examples/contracts`](../examples/contracts). Setup and semantics: [service README](../README.md). Field-by-field changes from 1.0: [MIGRATION.md](../../evaluation/recommendation-exploration-2026-10-23/MIGRATION.md).
